## 실제 연결 범위

`/dion`은 기존 Next.js16.4.3/React19.3.1에 추가한 경로다. `/`의 Iteration1 계산은 그대로 두고 새 진입 링크만 추가했다. 설치된 Next 문서의 Route Handlers·Server/Client Components·CSS 지침을 확인했으며 의존성/lockfile을 변경하지 않았다.

질문55개 원문과 개별 정의버전, 선택지, 생애단계, 결과 게이트를 원본 JSON에서 생성한 `frontend/src/lib/dion/catalog.json`에 보존했다. 실제 상세 입력은 NEW-01, LIFE-01, F11, F03, F04, F06, N01, N02, NEW-04, F09+F10+D08, F12, F13, NEW-03, NEW-02, NEW-05, NEW-06, F17의17개다. 나머지38개는 상세 입력/계산 미지원 안내다. F08은 해당자 질문 목록에 나타나지만 상세 수집 전에 미지원임을 알린다. 모든55개를 필수로 만들지 않는다.

빠른 기본11개와 부동산/채무 상세0~2개, 정밀 직접 진입 및5개 보충 카드를 제공한다. 상세 배열은 원래 항목 ID를 재사용하며 추가 항목에는 새 ID를 생성한다. 추가 확인 편집기는 현재 원응답의 ID에 연결하고 가상 사례의 사실값은 채우지 않는다. 고급 상세 편집에는 참조 ID/가정 입력이 필요해 일반 고객용 입력 단순화는 후속 과제다.

화면 금액은 만원, 전송 원문은 정확한 십진문자열과 원래 단위다. `00300.0000`을 문자열 그대로 보내고 서버 어댑터가 원 단위로 정규화한다. 화면 표시의 소수점 이동은 문자열/BigInt이며 차트 좌표에만 Number를 사용한다. 금융 산식·배정 판단은 모두 기존 Python 엔진이 수행한다.

원응답 필드의 KNOWN/UNKNOWN/NOT_ENTERED/NOT_ASKED/NOT_APPLICABLE/DEFERRED/DECLINED, 질문 정의·원문·선택지·기간·소유자·출처를 보존한다. 숨겨진 채무 상세를 삭제하지 않으며 ‘채무 없음’과 충돌하면 엔진 검증으로 보류한다. 카드 비우기는 NOT_ENTERED/null 새 수정본이다. 응답 진행률은 활성 분기의 응답 수/카드 수이며 계산 로딩은 불확정 표시다. 응답 완료는 금융 계산 가능 상태를 뜻하지 않는다.

## API와 버전 계약

브라우저는 같은 출처의 `/api/*`를 호출하고 Next rewrites가 백엔드8001로 전달한다. 기존 `BACKEND_URL` 설정이 있으면 그 값을 우선한다. `.env`는 수정하지 않았다.

|경로|요청/응답과 책임|
|---|---|
|POST `/api/fe/v1/preview`|기존 `DION-QUESTION12-ADAPTER-1.0` 문서 전체. `{integration_version, storage:NOT_SAVED, result}` 반환. 실제 순수 엔진 실행, 영속 저장/계획 채택 없음, `Cache-Control:no-store`|
|POST `/api/be/v1/cases/{id}/question-analyses`|인증 필수. `{expected_version,request_key,context,requested_outputs,scope_ref,confirmations}`. 실제 저장 원응답으로 고정 입력을 만들고 기존 분석 실행/receipt/불변 이력 테이블 재사용|
|GET `/api/be/v1/cases/{id}/analyses[/{run_id}]`|기존 조회 그대로. 새 경로의1.2/1.2.1과 기존1.3-engine 분석 모두 읽기 전용 조회|
|PUT/GET `/api/be/v1/cases/{id}/answers`|기존 카드별 전체 원응답 저장·복원 그대로. 새 필드 상태를 발명하지 않음|
|기존 POST `/analyses`|1.3-engine OUT-01/03 전용 그대로 유지|

`question-analyses.context`는 evaluation_on, scope, included_owner_ids, currency, timezone 및 선택 projection_start/end다. case_id/raw_snapshot_id/profile_version은 서버의 실제 저장 참조로 생성한다. 기본 UI requested_outputs는 OUT-01~05다. 미래 가정은 기존 명시 확인 계약 `DION-ADAPTER-CONFIRM-1.0`을 그대로 사용한다. 원질문 답변을1.3-engine으로 재표기하지 않는다.

엔진/배정/바인딩 버전과 원문 `calc_state`는 결과 응답을 그대로 표시·내보낸다. `input_version`은 서버 원응답 수정 순번, `run_id`는 불변 계산실행, `is_current`는 실행 시 입력버전과 현재 서버 입력버전의 일치다. SUCCEEDED는 실행 기록 성공이며 모든 출력 READY나 고객 채택을 뜻하지 않는다. 추가 가정이 달라도 원응답 버전은 같을 수 있으므로 화면은 문서 전체 서명으로 현재 작성값과 결과의 일치도 따로 판정한다.

이번에 추가한 `frontend_integration.version=DION-FE-INTEGRATION-1.0`과 `presentation_gates`는 **표시 연결 상태**다. N01의 부동산 보유/미확인/원응답 부재, N02 전세·월세에 따른 미연결 보증금 확인을 기록하고 관련 OUT-02/04/05 표시를 보류한다. 원래 엔진 상태·금액·결과를 고쳐 쓰지 않는다. OUT-03 부분 결과와 검토 JSON의 원문은 유지한다. 법정 규칙 활성0, 권장액 미정, plan_adopted=false, transaction_executed=false다.

JSON float/중복 키는 기존 exact parser에서422다. 기존 오류 본문 `detail.code`,401인증,409수정충돌,422계약오류,503인증/저장서비스 오류를 표시한다. 엔진 INVALID_INPUT/NEEDS_INPUT/NOT_SUPPORTED는 HTTP 성공 여부와 따로 표시한다. 응답 이상·연결 실패 시 샘플로 대체하지 않는다.

카드 저장은 부분 성공이 가능하다. 성공한 receipt/input_version을 기록하고 응답 유실 시 같은 request_key와 같은 본문으로 재시도한다. 충돌 시 로컬 작성값을 유지한다. 분석 재시도도 동일 입력에 동일 키를 사용한다. 입력 변경/새 요청 시 AbortController와 증가 순번으로 늦은 응답을 무시한다. 이전 결과는 최대20개 탭 메모리 또는 불변 서버 실행에서 확인한다.

복원은 최신 원응답만 편집 화면에 가져오고 과거 가정은 자동 재사용하지 않는다. 질문별 복수 소유자/기간 그룹이나 정의버전 불일치가 있으면 자동 병합하지 않고 명시 선택/마이그레이션이 필요하다고 거절한다. 기존1.3-engine 결과는 목록에서 읽을 수 있다. 로그인 UI는 미연결이며 access token 수동입력은 검토 패널에 한정한다. 토큰은 탭 메모리에만 보관하고 JSON/콘솔/localStorage로 내보내지 않는다.

## 검증 명령과 결과

Windows PowerShell에서 스크립트 정책으로 직접 실행이 차단되어 **현재 자식 프로세스에만** ExecutionPolicy Bypass를 적용했다. 시스템 정책을 바꾸지 않았다. 명령은 프로젝트 루트 기준이다.

```powershell
& (Get-Process -Id $PID).Path -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -Mode Core
& (Get-Process -Id $PID).Path -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -Mode Build
& (Get-Process -Id $PID).Path -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -Mode E2E -BrowserChannel msedge
& .\backend\.venv\Scripts\python.exe docs/questions/v1.2/check_question_design.py
```

서버 저장 E2E는 별도 PowerShell 창에서 임시 저장소를 실행하고 E2E 프로세스에만 URL을 설정한다. 이 도구는 `backend/tests/`에 있으며 운영 entrypoint에서 import하지 않는다. 프로세스 종료 시 임시 가상 DB를 정리한다.

```powershell
Push-Location backend
& .\.venv\Scripts\python.exe -m tests.fe_http_harness --port 8002
Pop-Location
# E2E 실행 창에서만:
$env:DION_TEST_BE_URL='http://127.0.0.1:8002'
```

검증 결과와 초기 실패 기록은 아래 완료 기록에서 구분한다. 원격 인증·DB 미실행을 통과로 표현하지 않는다. Build는 이 작업 소유 FE 서버를 확인하고 종료한 상태에서 실행했으며 기존 다른 프로젝트 서버는 건드리지 않았다.

초기 Core에서 v6 질문 카탈로그 hash 불일치와 Windows SQLite 테스트 연결 미종료를 확인해 원인만 수정했다. 초기 신규 E2E는 중복 질문 이동 이름/Next route announcer의 중복 role=alert 선택 때문에 실패해 고유 이름/정확한 locator로 보완했다. 개발 서버 전체 E2E에서는 `/api/sample-profile` 프록시 ECONNRESET 1건으로 기존 검사가 실패했다(20통과/1실패). 엔진 금액 오류는 없었고 해당 실패는 숨기지 않는다. 이후 최종 빌드의 production 서버에서 전체21개가 통과했다. 개발 프록시 끊김의 근본 원인을 해결했다는 의미는 아니며 재발 시 FE/BE 로그와 포트/소유 프로세스를 먼저 점검한다.

현재3000은 이번 작업이 시작한 production 서버(`npm.cmd run start -- --port 3000`과 동등),8001은 `app.be_server:app`이다. 테스트 전용8002는 검증 후 종료한다. 저장 검사에 사용하는 모의 인증은 제품 서버8001에 적용하지 않았다.
