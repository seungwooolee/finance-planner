필요한 후속 조치:

1. F15 제안필드를 자금별 공용 바인딩으로 확정: 현재 FE는 `investment_funds` JSON 안에서 날짜·상태 Field를 보존하고 `fund_id`/선택 메모 `label`을 FE 항목 구분용으로 쓴다. 원천자산·목표·기간의 의미적 매핑과 정규화는 BE 승인 필요. 경험 선택지의 `experience_products`와 저장 제안 `investment_experience_products`는 FE에서 명시 대응하며 과거 Q-ID로 자동 이관하지 않는다.
2. OUT-06 판정 API가 필요하다. 아래는 **구현되지 않은 응답 제안**이며 현행 API라고 해석하지 않는다. 실제 버전/정책 승인은 BE·정책 담당이 결정한다. 의향·능력·기간·경험·이해도를 별도로 판정하고 원응답 revision, 누락 ID, 이유, 상태, 정책 버전·승인 상태를 반환해야 한다.

```json
{"OUT-06":{"calc_state":"NEEDS_INPUT","policy_version":null,"policy_status":"NOT_IMPLEMENTED","risk_grade":null,"recommended_new_investment_krw":null,"missing_question_ids":["NEW-08"],"reason_codes":["LOSS_CAPACITY_UNKNOWN"],"evidence_answer_revision_ids":[],"product_allocations":[]}}
```

3. 상품 식별자·자산군·위험·비용·출처·확인일, 배정 예산·비중·금액·반올림 잔액, 목표/자금 연결·선정 이유를 공용 API에서 제공해야 한다. FE 임의 배분은 추가하지 않았다.
4. 어댑터1.1 저장 계산은 별도 통합. 해당 연결 후 복직·지급일·보호금 EXTRA, 연금/세금/상속 상세 입력의 지원 범위를 다시 맞춰야 한다. 이번 사례의 한 달 현재 현황 검증은 이를 대신하지 않는다.
