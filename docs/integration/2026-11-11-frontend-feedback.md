# 고객 입력 UX 1차 피드백 반영

## 이번 작업 계약

사용자 피드백: 상태 선택(입력한 값/모름/미입력 등)을 전면 재검토하고 금액 입력·질문을 쉽게 바꾼다. 진단 기준일은 새 진단의 오늘(Asia/Seoul), 구성원 별칭은 제거, 진단 범위+생활단계를 한 화면에 배치한다. 목표 선택과 목표금액/시점을 함께 묻고 일반 구조 편집기를 제거한다. 목표 없음 선택을 추가한다. 소득 기간 입력은 계산 의존성을 확인해 줄이고 일회성 소득 문구를 바꾼다.

원문55개/정의버전/원응답은 보존하고 UI 표현과 화면 묶음을 변경한다. 기본11개의 질문 계약을8개 고객 화면으로 묶으며 조건부 상세는 유지한다. UI 문구 버전은 DION-FE-COPY-1.1로 기록한다. 질문 통합은 원문 ID 통합이나 기존 답변 자동 삭제가 아니다.

계산 계약 확인: F03/F04는 동일한 명시 기준기간이 있어야 현금흐름을 계산한다. 시작/종료일 대신 월 선택 하나를 사용하고 같은 월의1일/말일로 변환한다. 신규 답변에 임의 소득 기간·일회성소득 여부를 확정하지 않는다. 기존 비표준 기간 응답은 보존하며 명시 월 변경 전 재표기하지 않는다. ‘상여금·선물처럼 이번에만 받은 돈이 포함됐나요?’로 YES/NO를 확인한다.

자산 완전성은 NEW-01의 현재 엔진 필수 필드다. 진단 첫 화면에서는 삭제하고 자산 단계의 쉬운 누락 확인으로 옮긴다. 확인 전 complete를 채우지 않는다. 고객이 선택한 목표 없음은 F11/F12/F13에 빈 목표 목록으로 명시하며, 기존 목표가 있으면 교체 확인과 되돌리기를 제공한다. 목표 제거 시 남은 목표 ID와 금액·날짜는 유지한다.

완료 조건: 빈 화면에서 상황→목표/금액→소득→지출 이동, 합쳐진 단계의 진행률, 숫자 원문·0/빈칸·선택적 나중응답 보존, 오늘 기준, 기존 가상 사례160/90·목표수정·저장 복원 회귀, PC/모바일 직접 확인. 금융 산식·새 인증·법정/상품 지원 확대는 범위에 포함하지 않는다.

## 원본 디자인과 이번 변경

Stitch 원본의 흰 카드·라벤더 배경·인디고 강조색, 왼쪽 단계 이동, 상단 진단 경로와 결과5뷰 구조를 유지한다. 첫 구현과 원본의 대응표는 [기존 통합 기록](2026-11-11-frontend.md#stitch-대조와-가상-자료-캡처)에 보존했다. 이번에는 사용자 피드백에 따라 입력11개를8개 화면으로 묶고, 목표 금액/날짜를 같은 카드로 옮겼다. 원본의 고정 추천상품·수익곡선이나 없는 계산 결과는 추가하지 않았다. 원본 HTML/PNG·질문 계약 JSON은 수정하지 않았다.

## 검증 기록

첫 Core 실행: pytest369통과/7skip, Ruff/pip check 통과 후 TypeScript import 누락1건으로 중단. 누락을 수정한 뒤 TypeScript/ESLint 개별 재실행 통과. 최종 Core/Build/브라우저 검사 결과는 아래 최종 확인에 기록한다.

개발 서버 첫 E2E:19통과/4실패.2건은 Next 프록시 ECONNRESET(새 입력과 기존 검산),1건은 모의 인증 저장 HTTP 요청 시간 초과,1건은 새 기준월 테스트의 예상 상태가 잘못된 경우였다. 실제 어댑터가 과거 기간에 연결된 미래소득 가정을 INVALID_INPUT으로 보류하는 근거를 직접 확인하고 테스트를 그 계약에 맞게 수정했다. 금융 산식/기존 정답을 변경하지 않았다. 당시 실패를 숨기기 위한 재시도나 가상 계산 응답은 추가하지 않았다.

첫 production Build 통과, E2E23통과(기존14+새화면9). 이후 검토용 비표준 기간 편집의 context 동기화와 투자선호 이동 버튼의 표시문구를 보완해 관련 검사를 추가했다.

## 남은 범위와 다음 작은 기능

이번 반영은 첫 고객 입력 흐름의1차 개선이다. 자산별 보유내역·대출/할부·미래 소득 가정·목표 적립 일정의 상세 입력은 아직 검토 중심이다. 소유자/계좌 참조와 미래 가정은 확인한 원장에 맞춰 검토 도구로 보완할 수 있으며, 정보가 없으면 계산을 보류한다. 이를 모두 고객용으로 완성했다고 보고하지 않는다.

다음 작은 기능은 **자산·대출 상세를 사람이 이해하는 항목/소유자 선택으로 바꾸는 것**이다. 소유자·기간·자산/계좌 연결과 원금/이자 분리를 먼저 계약으로 확인한 뒤 실제 엔진의 정상/누락/충돌 사례로 검증한다. 이후 결과 설명을 ‘현재 상황 → 부족한 정보 → 다음 행동’ 순으로 줄이는 작업이 필요하다.

실제 로그인/원격DB, 부동산·보증금 계산 연결, 세금·연금·상속 법정산식, 투자 적합성/상품 추천, 고객 채택·거래는 이번 변경으로 구현되지 않는다. 저장 검사는 tests 전용 모의 인증과 임시 SQLite 범위다.
