# DION 재무엔진 확장 명세 — FIN-CONTRACT-0.1

작성·조회일 2026-11-10 · Asia/Seoul · 현행 보완:7.3절 배정정책 DION-ALLOCATION-1.0 및 월 후보 산술. 공통 계약 스키마는0.1을 유지한다.

이번 사용자 요청으로 **세금·연금·상속을 엔진 설계 범위에 포함**했다. 포함 여부는 확정됐고, 아래 우선 지원 범위는 제안이다. **A1·B1에 이어 남은 네 배정정책도 사용자 위임으로 확정**했다. 현행 배정정책은 `DION-ALLOCATION-1.0`과7.3절이다. A1B1-0.1의 규칙/기대값은 부분 구현 이력으로 보존한다. 세율·공제·연금 산식·상속 규칙·투자 적합성과 세 모듈/전체 엔진 완성은 여전히 별도다.

## 1. 기준과 현재 상태

기존 `backend/app/engine.py`, `models.py`, `main.py`, 고정정답과 질문40/선택지304/영속Q-ID60/옛 설계37을 유지한다. 기존 앱은 기본 현황·주거목표 엔진이다. 자금원장 도구는 명시 후보를 검사하며 두 재무안을 생성하지 않는다.

| inheritance_cases[] | OWN_ESTATE/INCOMING·사건/가정일·확정상태·재산/채무 참조·가족·배분·증여이력·세금/비용·유입/지급일 | 설계만. 시나리오를 현재자산으로 승격하지 않음 |
| events[] | 고유 경제사건ID·원장 사건ID·기간·계좌·방향·내부이체 쌍·세금/비용·반영상태 | 기존 funding의 단일현금 경로 검사 재사용. 통합 사건원장 미구현 |
| versions | 입력/정의/엔진/정책/법령/외부 스냅샷·원문지문 | 부분 지원. 원응답·계산입력의 SHA-256·context 포함 |
| extension_payloads | 확장 초안의 원문을 보존할 별도 공간 | 불투명 보관만. 금액·권한·상속·연금 의미검사/계산에 사용하지 않음 |

### 값·날짜·지분 규칙

- 금액: 정수 원 단위 십진 문자열. 이번 파서는 입력 최대 40자리의 비음수 정수만 받으며 합계·차액은 임의정밀도 정수다. 기존 API의 1조 입력상한과 별개이며 새 서비스 한도 승인이 아니다. 원/만원 변환은 명시 단위가 있을 때만 어댑터가 수행한다.
- 공통 금액 객체: `{value, missing_status, basis, source_ref, omission_reason?}`. `KNOWN`은 `"0"` 포함 값 필수. UNKNOWN/NOT_ASKED/NOT_APPLICABLE은 value=null. NOT_APPLICABLE을 필수 금액의 0으로 계산하지 않는다. 생략 사유는 LATER/DECLINED이고 원응답도 보존한다.
- basis: USER_REPORTED / ESTIMATED / OFFICIAL_VALUE / SCENARIO / ACTUAL. `OFFICIAL_VALUE` 표시는 고객이 전달한 공식 자료값일 수 있으며 시스템의 법령 검증 완료 표시가 아니다.
- 자산·채무: owner_ids는 분석에 포함한 소유자만. `share_numerator/denominator`는 해당 범위의 지분이고 `TOTAL_VALUE`에만 곱한다. `SCOPE_SHARE`는 이미 반영한 값이다. 반원 등 정수 원 미만은 적용할 평가/반올림 규칙 확인 전 확정 보류한다.
- 이번 현황 집계는 평가일이 기준일과 같은 항목만 완전합계로 확정한다. 과거 평가액을 현재로 재평가하거나 자산을 소멸시키지 않는다. 원문 값과 사유를 남긴다. 고도화 시 원천별 평가기준을 별도 정책으로 관리한다.
- 사건일, 과세귀속연도, 법령효력일, 수령일, 세금납부일, 가용일은 별개다. 날짜를 모르면 임의 월말/오늘로 채우지 않는다. 당일 입출금 순서 미확인은 지급안전 판정을 보류한다.
- 같은 경제자산을 서로 다른 ID로 중복 등록한 것까지 자동 식별하지는 못한다. 후속 어댑터에 canonical ID/원천 매칭·합의가 필요하다. 가구 내부 공동자산은 하나의 원천을 참조한다.

## 4. 출력과 상태 계약

각 결과는 값·단위·계산상태·기준시점·범위·source/input/policy/legal 참조·미반영 항목을 가진다. 전체 초안에서는 `calc_state`와 자금충당·적합성·채택 상태를 분리한다. 0.1은 이 중 현황/현금흐름 일부와 원문/context/SHA를 반환한다.

| 상태 | 뜻 | 숫자 처리 |
| --- | --- | --- |
| CALCULATED | 해당 범위의 입력으로 산술 가능 | 값 반환. 법령검증·추천·채택 승인이 아님 |
| NEEDS_INPUT | 모름·미질문·완전성 부족·값 충돌 | 영향받는 확정값 null, 다른 결과 유지 |
| NEEDS_POLICY | 배정·투자 등 서비스 정책 미정 | 추천/생성 보류. 0.1의 지분 반올림 미정은 현황 NEEDS_INPUT과 세부 사유로 반환 |
| NOT_IMPLEMENTED | 범위에 포함했지만 코드 미구현 | 이번 세금·연금·상속 모듈의 실제 상태 |
| NOT_SUPPORTED | 구현한 모듈의 지원대상 밖 | 해외/복잡예외 등의 후속 지원경계에서 사용. 현재 파서는 해당 모듈 자체 미구현 |
| NOT_APPLICABLE | 확인된 분기 제외 | 제외 사유, 필요한 경우 null. 미구현과 구별 |
| INVALID_INPUT | 형식·ID·범위·정의 모순 | 해당 scope 오류. 모호한 금액을 조용히 보정하지 않음 |
| INTERNAL_ERROR | 엔진 자체 불변식 위반 | 금융 결과로 제시하지 않음. 내부 오류 처리 후속 |

부족액은 별도 feasibility=SHORTFALL이며 입력오류가 아니다. 완전한 자산/채무 없이 전체 순자산을 확정하지 않는다. 당장 투자할 수 있는 금액·미래 금융자산·은퇴 부족액·상속세 납부현금은 서로 다른 출력이다.

0.1 함수: `calculate_snapshot(document) -> dict`. 원입력을 deepcopy해 input_snapshot으로 보존하고 동일 JSON 의미·버전이면 같은 결과/SHA를 반환한다. 생성시각·run_id는 이후 호출자가 부여한다. 지원하지 않는 필드는 거절하고 초안 확장은 extension_payloads에만 보존한다. extension_payloads는 검증 완료 입력이 아니다. 전체금융자산 구성, 현재 투자가능액, 미래 반복소득, 계획채택은 생성하지 않는다.

## 5. 모듈 간 중복 방지와 사건 설계

| 위험 | 공통 처리 계약 |
| --- | --- |
| 계좌 합계 + 보유상품 | 부모 합계만 집계. 완전상세 불일치는 확정합계 보류, 부분 차액을 현금 추정 금지 |
| 월 생활비에 원리금/납입 포함 | 확인된 포함액만 분리, 정규생활비+의무상환을 각각 한 번 사용 |
| 세후소득에서 세금 재차감 | basis=NET 및 포함세금 참조. 이미 차감된 원천세는 별도 현금유출 금지, 추가 납부만 별도 사건 |
| 확인된 세금이 없음 | 미확인을 0으로 간주 금지. 세전 참고결과와 세후 null을 분리 |
| 세액 산출일과 납부일 혼동 | 세금채무/비용 인식과 실제 납부현금을 구분. 추가세금은 납부일 현금경로에 1회 |
| 연금잔액 + 계좌잔액 | pension.balance_asset_ref로 현재 자산 원천 참조. 독립 자산 추가 금지 |
| 연금 납입 + 자산증가 | 기존 납입 contribution_id와 계좌 이체 쌍 참조. 개인 범위 내부이체는 자산 순증 0, 평가손익과 분리 |
| 세후급여 안의 공적연금 보험료 | 이미 공제된 본인부담분은 월 가용금에서 재차감 금지. 사용자 추가납입/임의납입과 구분 |
| 연금 현재 수령 + 미래 예상수령 | income_source_id로 전환일/기간 연결, 같은 월에 복제 금지 |
| 연금잔액에서 지급 + 별도 외부소득 | 보유계좌 인출이면 잔액감소/현금증가. 외부 연금급여와 구분해 순자산 이중증가 방지 |
| DB/국민연금 예상액을 현재 금융자산 처리 | 실제 인출가능 잔액으로 확인되지 않은 예상급여/가입기록은 현재자산으로 생성 금지 |
| 본인 사후재산 + 현재자산 | OWN_ESTATE는 현재 원장 또는 별도 사망시점 시나리오를 참조. 현재자산에 재가산 금지 |
| 받을 상속 + 이미 받은 자산 | 수령 economic_event_id와 resulting_asset_id 연결. 이미 잔액 반영된 유입은 다시 가산 금지 |
| 가구 내부 상속 | 이전자/수령자가 모두 집계범위 안이면 범위 내부 소유권 이전. 가구자산 순유입으로 더하지 않음 |
| 양쪽 상속 방향·세금 모듈 | 동일 estate_case_id/taxable_event_id를 참조. 상속 모듈은 세금 모듈 결과를 소비하고 세액을 중복 차감하지 않음 |
| 확정/미확정·상속일/현금화일 | 상속개시·분할확정·수령·현금화는 별개 상태. 미래 미확정 상속은 현재 확정 투자한도에서 제외 |
| 동일 사건 재전송 | 같은 ID/같은 내용 1회, 같은 ID/다른 내용 충돌. 기존 원장 도구 검사 재사용, 다계좌 통합은 후속 |

위 전체 사건 규칙은 설계 계약이다. 0.1 실행 구현은 부모/자식 대사·지분·현재자산 origin 제한·생활비 정규화까지다. 연금/세금/상속 사건을 이미 통합 처리한다고 표시하지 않는다.

### 공식 근거와 활성화 게이트

[법령·근거 등록부](financial-engine-rule-registry.json)에 URL·조회일·확인 범위·검증상태·적용연도·시행기간·대상·예외·반올림 필드를 기록한다. **활성 규칙은 0개**다.

- 국세청 금융소득 안내에서는 소득종류·수입시기·원천징수시기를 별개 검토 축으로 확인했다. 실제 세액 산식을 이번에 구현하지 않았다.
- 국민연금공단 자료에서는 공식 예상연금 조회와 수급 시기 확인 경로를 확인했다. 고객 본인의 조회·인증·자동연동은 하지 않았다.
- 국세청 상속세 흐름도에서는 재산·채무·비용·사전증여·공제의 구분을 구조 참고로 사용했다. 상속세 과표나 세액을 단순 순재산 비율로 구현하지 않았다.
- 국가법령정보센터 검색 목록과 접근한 연혁 본문에 서로 다른 시행일 표시가 있어, 적용 사건별 연혁·부칙·하위규정 검토를 미완료로 남겼다. 2026 규칙이 검증됐다고 선언하지 않는다.

각 규칙 활성화 전: 사건 유형/납세자/적용연도 고정 → 법령 본문·부칙·하위규정·공식 안내 대조 → 국세/지방세·예외·반올림/납부일 확정 → 독립 공식 사례 → 시행일 전/당일/후 및 예외 검사 → 활성 버전 등록 순으로 진행한다. 개정안은 ENACTMENT_PROPOSAL, 공포됐지만 미래 시행인 규칙은 ENACTED_FUTURE, 해당 사건에 유효한 규칙은 EFFECTIVE로 분리한다. 자동 최신판 대체는 금지한다.

### 7.1 이번 부분 구현의 정확한 계산 규칙

`docs/dion/09_UPDATED_FILES/tools/allocation_policy.py`는 기존 `funding_ledger.py`를 직접 재사용한다. 원장 전체를 다시 만들거나 기존 도구의 정책 미정 게이트를 바꾸지 않는다. 이 함수는 입력 후보의 월 납입/투자/현금 벡터를 **검토용 후보**로 계산한다. 실제 계획 채택·계좌변경·두안 전체 자동생성은 아니다.

1. 원천별 초과배정·동일자산 중복·가용시점과 월 입력 형식을 기존 도구로 검사한다. 목표미정은 월 대사 오류와 함께 있더라도 NEEDS_INPUT으로 반환하고 생성하지 않는다.
2. 보호목표는 고객이 명시한 단일 금액이다. 평가일 현재 가용 CASH 원천의 PROTECTION 배정만 현재 확보액으로 센다. 비현금 보호금 적격성은 NOT_SUPPORTED, 목표/금액/H 미확인은 NEEDS_INPUT이다. 서비스 보호최소금액·개월은 생성하지 않는다.
3. 기존 유지납입 C, 같은 목표의 기존분을 뺀 추가목표 G, H를 먼저 확인한다. R = 세후소득−정규생활비−의무상환−C−G−H. R<0이면 보호금을 투입하거나 기존자산을 매각하지 않고 부족을 보존한다. **보호와 목표가 동시에 부족할 때의 전체 우선배정·목표변경은 이번 범위 밖**이다.
4. 목표와 기존납입 충돌 시 B1을 적용해 유연납입 검토목록과 필요한 감액 총액을 반환한다. 고객허용 ALLOWED·계약 CLEAR·세금/비용 영향 없음 NO_IMPACT·동일 입력버전·최소 유지액·감액한도를 모두 명시한 시나리오 항목만 감액 후보가 된다. 하나라도 모르면 NEEDS_INPUT, 확인된 영향이 있으면 비용/세금 통합 전 감액 적용을 지원하지 않는다. 이 플래그들은 입력의 시나리오 전제이며 법령·약관 검증 완료 표시가 아니다.
5. 여러 후보의 감액 순서/비율은 승인되지 않았으므로 자동 선정하지 않는다. `requested_reductions`로 항목·금액이 명시된 경우만 계산에 반영한다. 필요한 부족액보다 더 줄여 신규 투자여력을 만드는 감액은 거절한다. 목표·보호와 연결된 납입의 감액도 이번 기능에서는 제외한다. 허용 감액만으로 부족을 해소할 수 없으면 INFEASIBLE을 반환하고 목표/기한을 자동 변경하지 않는다.
6. R≥0이면 추가보충 = min(R, max(기초 보호부족−같은 보호목표의 기존 유지납입, 0)). 기존 보호납입은 월 C에 한 번 포함하고 부족액 보충에도 한 번만 인정한다. 추가보충을 새로운 원금자산으로 더하지 않는다.
7. 기초 보호부족>0인 월은 신규투자 상한0, 보충 후 남는 R은 명시 현금으로 둔다. **보호금을 채운 당월의 지급/입금 순서를 확인하지 못하는 월 모델의 제한**이다. 일별 모델에서 보충 완료 후 투자 가능 여부는 후속 검증한다. 다음 기간의 새 기초 보호금이 확인돼 부족0이면 남은 예산을 정책상 상한으로 반환한다. 신규 일시투자도 기초 보호부족 중에는 차단한다.
8. 상한이 양수여도 권장투자액은 null이다. 보충 후 잔여는 현금으로 표시한다. 전체 생성정책은 NEEDS_POLICY를 유지하고, 기존 원장으로 새 월후보의 대사차이0을 재검사한다. 기간 중 현금 경로는 별도 상태이며 월 대사 통과로 실제 지급안전을 판정하지 않는다.

현재는 KRW·SCENARIO·명시 월예산·단일 CASH 보호목표만 지원한다. 현황계약 FIN-CONTRACT-0.1에서 이 원장으로 자동 이관하는 어댑터는 아직 없다. 매달 기초잔액을 자동 누적하거나 고객의 원응답을 0으로 채우지 않는다.

### 7.2 입출력 계약과 고정 사례

입력은 기존 funding 문서 `{context, stock, monthly, timing}`에 `allocation_policy`를 추가한다. context는 기존 case/profile/snapshot/plan/version·SCENARIO·strategy_id를 유지한다. 평가일은 timing.opening_on과 같아야 하고 예산월은 평가월 이전일 수 없다. 기존 monthly.targets에는 GOAL만 넣고 추가 PROTECTION은 A1 함수가 산출한다. 기존 보호납입은 `purpose=PROTECTION, target_id=protection_target_id`로 같은 목적을 명시한다.

`allocation_policy` 필수 필드:

| 필드 | 의미 |

| evaluation_on | 평가/기초잔액 기준일 |

### 근거와 확정의 한계

CFPB의 비상자금 안내는 필요액의 개인 상황 의존성과 입출금 시점 확인을 설명한다. Florida Department of Financial Services의 교육자료는 생활비3~6개월을 예시한다. 조회일은2026-11-10이다. 이는 한국 법령·국내 기관의 의무 최소기준이 아니며 DION의3개월 최소·운영1개월·50/80%를 직접 검증하지 않는다. 후자의 숫자는 이번 위임으로 선택한 초기 서비스 템플릿이고 최적값·수익보장으로 표시하지 않는다.

- [CFPB 비상자금 안내](https://www.consumerfinance.gov/an-essential-guide-to-building-an-emergency-fund/)
- [Florida DFS 비상자금 교육자료](https://myfloridacfo.com/ymm/LifeEvents/HandlingTheUnexpected)

정책 근거는 `data/allocation-rules-v1.json`에 분리했다. 세율·공제·연금·상속 법령규칙의 활성 건수는 여전히0개다.3개월 보호와1개월 운영은 별도 목적이므로 최소 합계4B가 필요하며, 같은 현금잔액을 양쪽에 중복 배정할 수 없다. 실제 지급 달력에서 더 큰 운영현금이 필요하면 별도 상향 후보와 근거를 기록하고 부족을 남긴다.

### 확정 산식·시점·예외

1. B=정규화된 필수생활비+확인된 불가피 의무상환. 보험료 등 중단불가 생활 지출은 필수생활비에 한 번 포함한다. 별도 의무지출이 누락된 입력은 이 계산에 연결하지 않는다. 필수생활비≤전체 생활비이며 포함관계·범위·기간이 같아야 한다. B의 기초나 고객 선택 상태가 모르면 NEEDS_INPUT이다. 고객 보호/운영 추가요구 없음이 확인된 경우만 고객 선택액0을 쓴다. 기존 직접금액 계산의 부분 결과는 보존하지만 새 서비스 최소는 B 없이는 확정하지 않는다.
2. 적격 보호/운영 기초배정은 평가일 현재 사용 가능한 CASH만 센다. 현재 원장 적격성이 검증되지 않은 연금잔액·보증금·미확정 상속·미매도 상품을 넣지 않는다. 기존 현금을 목적별로 재배정하는 자동 기능은 이번 월 정책에 포함하지 않는다.
3. C는 변경 전 기존납입이며, 항목·금액·허용/계약/비용 조건을 명시한 B1 시나리오만 C를 줄인다. 기존 보호납입은 C에 한 번 차감하고 보호부족에도 한 번만 인정한다. 같은 목표의 기존분은 필요 총납입에서 빼 추가액만 배정한다. 보호/목표 연결 납입은 자동 감액하지 않는다.
4. S=세후소득−전체 정규생활비−의무상환. S−C의 음수는 그대로 부족으로 반환한다. 양수이면 위 우선순위대로 `min(잔여,필요액)`을 배정하고 각 미충당액을 분리한다. 추가 보호는 고객 목표 전체까지 먼저 보충한다. 보호기한이 없는 보충 중 상태와 이번 기한 목표 미충당은 구분한다. 복수 목표의 우선순위 생성은 이번 코드의 지원 범위 밖이다.
5. A1에 따라 **기초 보호부족이 있는 달은 보충 완료 여부와 관계없이 신규투자0**이다. 같은 시점 제약을 운영현금 보충월에도 적용한다. 다음 기간 기초잔액이 확인되면 다시 계산한다. 월말 보충액을 그달 초 지급의 재원으로 쓰지 않는다.
6. 보호·운영 기초충족, 이번 목표충당 후 R을 신규투자 예산상한으로 반환한다. 기본 투자예산은 안정 `floor(R×50/100)`, 확대 `floor(R×80/100)` 원이며 나머지는 추가현금이다. 원 미만은 투자액을 내림하고 정확한 차액을 현금에 둔다. 확인된 고객 투자희망 상한·손실여력·기간·상품/세금 제약은 후속 적합성 모듈에서 더 낮출 수 있고, 차액은 현금으로 돌린다. 검증 전 실제 권장투자액은null이다.
7. 50/80%는 신규 월자금 및 적격성이 검증된 신규 목돈의 **예산 템플릿**에 적용하는 설계다. 목돈은 보호·운영·목표·다른 의무의 원천별 배정을 먼저 완료해야 하며 비현금 매각·기존 보유 교체는 자동 생성하지 않는다. 이번 실행 코드는 월자금만 구현하고 목돈 템플릿 자동 적용은 NOT_IMPLEMENTED다.
8. 두안의 원입력·기준일·정책·보호/목표·기존납입은 동일하다. 이번 템플릿은 생활비 자동 감축을 하지 않는다. 별도 허용된 지출 감축 후보는 기존 expense_change 검사를 거친 새 시나리오로 비교한다. 목표 미정이면0으로 가정해 투자안을 만들지 않는다.
9. 검토 후보·고객 채택·실제 실행을 구분한다. 월 대사 통과는 지급일 안전·수익성·법령·투자 적합성 통과가 아니다. 기존 funding 도구의 구버전 NEEDS_POLICY 메타데이터는 보존하며 새 도구의 `policy_state=DECIDED`와 구분한다. 정책 결정 완료와 전체 엔진 구현 완료도 구분한다.

## 9. 생애단계·최소입력 질문 v1.2 — 2026-11-10
