최신 보완: 포트폴리오 출력 형식 v1.2 · 제29~35절 · 2026-11-02
확정 · 기존 보유자산 재구성과 결과 표시 · 2026-11-03
확정 · 대상과 기본 표시: 예적금·주식·채권·ETF·펀드 등 금융자산의 기존 보유와 신규 투자금을 함께 고려해 재구성한다. 보험·연금은 이번 MVP의 수집·진단·추천·재구성 대상에서 제외하며 보험·연금 전용 질문·카드·상품 및 연금저축·IRP 제안을 제공하지 않는다. 제외 자산을 0원으로 간주하지 않으며 결과 합계는 ‘분석 대상 금융자산 기준’으로 표시한다. 은퇴기에도 이 범위의 생활비·확인된 소득·인출·투자 흐름을 다루며 종합 노후준비 진단으로 표시하지 않는다.
기본 포트폴리오는 현재/제안 구성·자산군별 비중과 금액·대표 상품·핵심 이유를 제공한다. 개별 상품별 매수·매도 금액·수량은 제시하지 않는다. 매도·교체 허용 여부를 일괄 사전 질문하거나 기본 카드에 길게 설명하지 않고 하단 AI 상담과 상세보기로 연결한다. 다만 매도·해지에 의존하는 안에서 비용·세금·해지 조건·고객 실행 가능 여부가 미확인이면 확정 실행안으로 처리하지 않고 해당 시점에 필요한 확인을 요청한다. 설명 위치를 옮기는 것과 검증 생략을 구분한다. 제안은 실제 보유·채택·실행 기록을 자동 변경하지 않는다.
예상 결과는 원금 기준 자금 변화·최우선 목표 부족액을 기본 제공한다. 수익률 가정 결과는 고객이 펼쳐볼 때 제공하며 가정·기간·비용·세금 반영 범위를 함께 표시한다. 근거 없는 예상수익률·세율은 생성하지 않는다. 보유자산을 유지하는 기준안과 재구성안을 동일한 입력·시점·가정으로 비교한다. 원금 기준은 수익률 예측이 아닌 계산상 비교이며 실제 원금 보장을 뜻하지 않는다.
원본 제30절 소비자 제공 예시의 기존 세 안·생활비 감액·상품별 배정금·신규금만 제안하는 설명은 개편 전 사례로 보존한다. 현행 설계는 재무계획 2안·기존 보유 포함 재구성·자산군 단위 배정 원칙을 우선하며 해당 예시의 수치를 새 추천값으로 사용하지 않는다.
확정 · 재무계획 2안과 투자 구성 연결 · 2026-11-03
재무계획은 ‘안정 중심’과 ‘투자 중심’ 두 가지다. 두 안은 같은 고객정보·기준일·생활비·목표 시점·공통 자금 제약으로 비교한다. 필수 생활비·의무상환·필수 목표자금·최소 비상자금을 공통으로 확보한 뒤 남는 자금에서 안정 중심은 추가 현금 여유, 투자 중심은 투자 가능한 장기자금 배정을 우선한다. 생활비·목표 시점은 고객이 변경에 동의했을 때만 조정하며 변경 조건을 표시한다. 투자 중심이라는 이유로 위험등급을 높이지 않는다. 실제 배분 금액·현금 여유 기준·산식은 후속 정책 설계·검산에서 확정한다.
투자성향 5단계와 투자 구성 3유형(안정 중심형·균형형·성장 중심형)은 재무계획 2안과 별개다. 화면 3 ‘금융자산’에서 고객 조건에 맞는 투자 구성 하나를 기본 제안한다. ‘다른 구성 보기’에서 적합한 범위의 대안을 비교하며 부적합한 구성은 선택을 제한하고 이유를 설명한다. 투자 제안이 불가능하거나 필수 정보가 부족하면 구성을 강제로 만들지 않고 보류·추가 확인을 안내한다.
계획·투자 구성의 미리보기와 실행계획 명시 채택은 구분한다. 첫 화면 요약과 화면 3 상세는 같은 선택 결과를 참조한다. 아래 기존 3안/PORT-01~03 설명은 개편 전 참고이며 현행 2안 UI 생성 기준으로 사용하지 않는다. 기존 식별자·채택 이력·실적·검산 사례를 삭제하거나 새 2안의 ID로 재해석하지 않는다. 원장·상세 구현 명세·코드의 이관과 정책 검증은 후속 작업이며 이번 문서 결정만으로 완료되지 않는다.
1단계 화면 설계 결정 · 2026-11-03
확정: 첫 화면은 현재 보유 자산을 먼저 정리한다. 계획을 선택하기 전에는 특정 계획의 제안 투자 구성·핵심 이유를 표시하지 않고 계획 선택 안내를 제공한다. 계획 선택 후 해당 계획의 투자 구성과 핵심 이유를 요약한다. 실제 보유와 미실행 제안은 별도 표시한다.
확정: 투자 제안의 상세와 대표 상품 제시는 화면 3 ‘금융자산’에서 제공한다. 국내 제안 대상은 ETF·개별주식·채권·펀드·예적금이다. 해외시장 투자 제안은 국내 상장 ETF와 국내 판매 인덱스펀드로 제한하며 해외 거래소 상장 상품·해외 개별주식·개별채권 직접 제안은 제외한다. 상장 상품은 국내 상장 여부를, 일반 인덱스펀드는 국내 판매 여부를 구분해 확인한다. 국내 상장이라는 이유로 기초자산까지 국내이거나 환율 영향이 없다고 가정하지 않는다. ISA·연금저축·IRP는 상품과 구별되는 계좌 유형으로 연결한다. 상품 범위의 결정과 실제 상품 사실·적합성·계좌별 취급 가능 여부·데이터 이용 검증은 구분한다.
화면 용어: ‘현재 자산’은 확인된 보유 상태, ‘제안 투자 구성’은 아직 실행되지 않은 계획, ‘대표 상품’은 제안 구성과 연결한 실제 상품 후보다. 요약과 상세는 같은 계획·입력·정책 버전을 참조한다.
유지: 두 가지 재무계획(안정 중심·투자 중심)의 비교·명시 채택, 자금 제약·투자 적합성 확인, 실행·사후 점검을 연결한다. 요약을 볼 계획의 선택은 미리보기이며 실행계획의 명시 채택과 구분한다. 채택한 계획이 있으면 기본 요약에 연결하고, 다른 안을 미리 볼 때는 미리보기 상태를 표시한다. 요약 표시만으로 현재 보유액이나 채택 기록을 바꾸지 않는다.
확정: 제안 투자 구성은 자산군별 비중·금액으로 표시하고 각 자산군 아래에 대표 상품·선정 이유·주요 위험·비용을 연결한다. 개별 상품별 투자 배정금·매수 수량은 제시하지 않는다. 첫 화면은 선택한 계획의 요약, 화면 3 ‘금융자산’은 상세를 제공한다. 표시 수준에 대한 결정이며 실제 배분 비중·금액의 산정 정책은 3단계에서 검증한다.
적용: 이 결정은 아래 기존 A~D 영역 설명보다 화면 배치에 우선한다. 화면 번호 1·3은 고객 화면을 뜻하며 문서 절 번호·영역 ID와 혼용하지 않는다. 나머지 화면의 순서·경로는 후속 설계에서 연결한다.

0. 문서 목적과 적용 원칙
이 문서는 팀원이 작성한 5단계 투자 포트폴리오·40문항 설문·Q35 산업선호 시안을 참고하고, 「dion | 데이터·시나리오 통합 검증·수정안 v2026-11-01」의 기존 데이터 계약·시나리오·계산 명세와 충돌하지 않도록 향후 통합 시트를 수정하기 위한 기준이다. 실제 Google Sheet·앱·기존 설계 원본은 이 문서 작성으로 변경되지 않는다.
핵심 목표: (1) 고객의 재무상태 진단과 목표별 실행계획, (2) 투자 가능 자금 내 개인화 자산배분 포트폴리오, (3) 선택한 산업군과 대체 산업군에 대한 데이터 기반 분석·기업 후보 비교, (4) 세 가지 재무실행 전략 비교, (5) 실행·사후 점검의 일관된 연결.
문서상 의사결정 표기: [확정] 사용자와 합의한 방향 / [권고] 개발 전 승인·수치 검증이 필요한 권장 설계 / [검증 필요] 세법·법률·API·점수 및 비중 등 외부 확인 또는 별도 정책 결정 필요 / [현행] 통합 시트에 이미 있는 계약.
1. 결론 및 아키텍처
[확정] 재무설계 기능과 투자 포트폴리오 제안 기능을 모두 유지한다. 둘 중 하나로 축소하지 않는다. 재무설계 결과가 보호·목표·투자가능 자금의 범위를 결정하고, 투자 포트폴리오는 그중 실제 투자 가능한 재원에만 적용된다.
[확정] P1 안정형, P2 안정추구형, P3 중립형, P4 적극투자형, P5 공격투자형이라는 다섯 단계의 '선호 투자성향' 분류를 유지한다. P1~P5 자체를 세 단계로 압축하지 않는다.
[확정/현행] 재무설계 실행 대안은 별도의 세 안으로 비교한다. 통합 시트 PORT-01=안정 우선안, PORT-02=현재 생활 유지안, PORT-03=목표 달성 우선안을 기준으로 한다. 이는 P1~P5를 3개의 위험등급으로 재분류하는 절차가 아니다. 세 안은 동일한 고객정보·기준일·제약조건하에서 자금 사용의 우선순위와 목표 시점·생활 여유 등을 비교하며, 위험 한도를 높여서 억지로 목표를 달성시키지 않는다.
[현행] 업무 흐름은 PROC-01 관계 정립 → PROC-02 정보·목표 → PROC-03 분석·평가 → PROC-04 제안·선택 → PROC-05 이번 달 실행 → PROC-06 사후 점검을 보존한다. '미리보기'와 '명시적 채택'을 분리하고 채택한 계획의 버전·실행 실적·수정 이력을 보존한다.
2. 설문 변경 및 식별자 충돌 방지
2.1 Q12와 Q32의 선택
[확정] 구 「설문40문항」의 Q12(투자금 20% 하락 시 예상 행동)를 유지하고, 구 설문의 Q32(최대 손실 허용률)를 제거하는 방향이다. 구 Q12는 현재 통합 시트의 Q-045 / loss_response와 내용상 대응한다. 단, 구 Q12와 통합 Q-045의 선택지 차이(전량/일부 매도/유지/추가매수 vs 매도/기다림/추가매수/모름)는 이관 규칙 및 질문 문구 검토가 필요하다.
절대 주의: 통합 시트 Q-032는 debt_balance_krw(대출 원금 잔액)으로서 구 설문 Q32와 완전히 다르다. 통합 Q-032는 삭제하거나 재번호화하지 않는다. 통합 Q-122 loss_affects_essentials(손실이 생활·상환·단기목표에 미치는 영향)도 별도 필수 안전 질문이므로 유지한다.
[권고] Q-045 하나만으로 P1~P5를 확정하지 않는다. 투자목적/선호 Q-044, 투자 경험 Q-042·Q-105, 장기자금 사용 가능기간 Q-117, 생활영향 Q-122, 재무현황을 함께 활용한다. 예상 행동과 실제 행동은 다를 수 있으므로 Q-045는 위험선호의 구성요소이지 단독 판정 근거가 아니다.
2.2 Q35 산업 선호와 제외 정보
[확정] 구 「Q35_산업선호_포트폴리오연결」의 의미를 채택한다. 고객에게 선호 산업을 최대 3개 선택하도록 하고, 선택 산업에 대한 AI 분석·추천 적합성 피드백·대체 산업 제안을 제공한다. 산업 미선택/잘 모르겠음도 허용하고, 선택 수를 반드시 3개로 채우도록 강제하지 않는다.
식별자 처리: 구 Q35는 구 40문항 체계의 라벨일 뿐, 현재 통합 시트의 고유 Q-ID와 자동으로 같지 않다. 현재 02_고객질문의 활성 Q-ID 60개 및 03_데이터명세를 기준으로 신규 고유 Q-ID를 배정하거나 기존 설문 교체 여부를 승인받아야 한다. 통합 시트에서 Q-035가 존재한다고 가정하거나 Q-123을 덮어쓰지 않는다. UI에 표시할 문항 번호 '35'와 API의 영속 Q-ID도 구분한다.
[확정] 기존 제외·비선호 상품 정보는 독립 유지한다. 현행 Q-123 restricted_assets는 유지하되 산업 선호와 별도의 필드로 관리한다. 제외 조건은 후보 선정에 우선 적용한다. 상품명만이 아니라 기초자산·상장국·통화·환노출·구조까지 태그로 검증한다.
산업 후보 예시 코드: EQ_SEMI, EQ_BIGTECH, EQ_AI, EQ_ROBOT, EQ_SHIP, EQ_DEFENSE, EQ_BIO, EQ_BATTERY, EQ_ENERGY, EQ_FINANCE, EQ_AUTO, EQ_INFRA. 구 ETF카테고리의 EQ_TECH와 EQ_BIGTECH는 ID 불일치가 있으므로 표준 코드/별칭 매핑을 확정한다. 산업 카테고리와 실제 ETF 자산군 코드를 동일하게 취급하지 않는다.
3. 위험선호도와 투자 여력의 연결
3.1 두 평가를 분리
[확정] 내부적으로 (A) 심리적 위험선호도, (B) 재무상태 기반 투자 여력·손실감당 가능성, (C) 자금 사용기간 및 목표 제약을 별도 평가한다. 결과는 서로 다른 데이터 필드로 저장하고 고객의 P1~P5 선호유형을 몰래 바꾸지 않는다.
(A) 위험선호도: Q-044 risk_preference, Q-045 loss_response, Q-042 투자 경험, Q-105 경험한 상품 등. (B) 투자 여력: 월 순현금흐름 CALC-01~03, 비상금 CALC-07, 일시 투자 가능액 CALC-08, 월 투자 가능액 CALC-09, 부채/소득안정성, 손실 시 필수생활 영향 Q-122. (C) 기간·목표 제약: Q-113~115 목표, Q-117 투자 가능기간, 지급일 현금흐름 CALC-06, 목표 유동성 G-06.
[권고] 처리 순서: ① 데이터 완전성 확인 → ② 필수생활·의무상환·보호금·가까운 목표자금 분리 → ③ 투자 가능 금액 산정 → ④ 선호 투자성향 P1~P5 판정 → ⑤ 투자 여력 및 목표기간의 위험 상한 판단 → ⑥ 허용 범위 내 기준 포트폴리오 생성/조정 또는 추천 보류. 실제 기준 점수·컷오프는 확정하지 않았으므로 임의 수치 사용 금지.
[확정] 고객에게 '경제적 위험감수능력이 낮음'처럼 능력을 평가하는 표현을 내보내지 않는다. 화면 표현은 '투자 여력 분석', '적합한 투자 범위', '우선 확보할 자금'을 사용한다. 단, 제약이나 추천 보류 사실은 명확히 설명한다.
예: '고객님의 투자 선호는 공격투자형입니다. 다만 예정된 주거자금 지출과 필수 자금 확보를 고려하면, 일부 자금을 우선 보전한 뒤 장기 투자 규모를 결정하는 전략이 더 적합합니다.' 투자 선호(P5)와 실행 제안(제약 반영)을 별도 노출.
3.2 추천 가능/보류 규칙
[권고] 차단·보류 조건: 투자기간과 자금 사용시점 충돌, 필수지출/대출상환에 손실이 미치는 영향, 보호금 중복 배정, 월 잉여현금 부족, 출처·기준일 미검증, 제외 상품 포함, 상품 위험 구조 이해 미확인. 상태는 ALLOWED / CONDITIONAL / NEEDS_INPUT / REVIEW_REQUIRED / INFEASIBLE / NOT_SUPPORTED 등 기존 시트 상태 계약과 정렬한다. '동의함'만으로 제약을 해제하지 않는다.
[권고] 비상금 목표개월, 허용 위험 상한, 스트레스 손실률, 위험성향 점수 가중치, 상품별 상한은 임의 확정하지 않는다. 독립 검산 가능한 정책표와 승인 담당·버전이 있어야 숫자를 입력한다. Q-045의 20%는 가상 행동 질문이지 확정 손실률이나 안전 기준이 아니다.
4. P1~P5 기준형과 자산배분 설계
[참고: 팀원 원안, 확정 비중 아님] P1 주식10%/채권70%/현금성20%; P2 30/55/15; P3 50/40/10; P4 70/25/5; P5 85/10/5. 5개 기준형은 위험성향의 초기 출발점으로만 보존한다. 어떤 고객에게도 자동 최종 배분값으로 적용하지 않는다. 채권·현금성으로 분류했다고 원금보장이라고 표현하지 않는다.
[확정] 구 고정 코어/위성 비율(P1 0%, P2 10%, P3 20%, P4 30%, P5 40%의 주식 내 위성 비중)과 산업 1~3개 균등 배분은 폐기 대상이다. 산업 선택 개수만으로 투자금액을 배분하지 않는다. 새로운 종목·산업 편입 비중은 적합성, 기존 보유노출, 분산과 집중도 검증, 거래비용·세금, 실제 사용기간을 고려하되 상세 상한은 [검증 필요]로 남긴다.
[권고] 포트폴리오 구성은 (i) 자산군별 목표 비중, (ii) 각 자산군의 ETF·현금성 상품 등 후보, (iii) 별도의 관심 산업 및 개별주식 비교 후보를 층으로 나눈다. 산업/종목 후보가 있다고 반드시 편입할 필요는 없다. 0개 추천도 정상 결과이다. 예상수익률·최적비중을 AI가 근거 없이 생성하지 않는다.
[현행 연계] PORT-04(보유자산 목적 배정), PORT-05(월 가용자금 배분), PORT-06(투자금 내부 구성), PORT-07(동일 조건 비교), PORT-08(미리보기·채택·버전)를 공통 엔진으로 재사용한다. 시트의 '두 포트폴리오' UX-11은 현재자산 배분과 제안 투자구성을 비교하는 뜻이므로 'P1~P5 대 세 안'과 혼동하지 않도록 UI 설명을 갱신한다.
5. Q35 → 산업 분석 → 기업 후보 비교 엔진
5.1 산업 평가와 고객 적합성 평가 분리
[확정] 산업평가 엔진은 성장 요인·실적 추이·산업 구조·경기 민감도·정책/규제·주요 위험·밸류에이션 수준·자료 최신성을 분석한다. 고객 적합성 엔진은 투자 가능 기간, 자금 규모, 위험 제한, 기존 노출, 제외상품, 상품 이해도, 거래 및 세금 영향을 별도로 판정한다. '산업 전망 긍정'은 '고객에게 매수 추천'을 의미하지 않는다.
[권고] 처리 파이프라인: 선택 산업 식별 → API·공시·통계 수집 → 데이터 출처·발표일·실적 기준기간 확인 → 정량 분석/정성 분석 → 산업별 긍정·부정·불확실 요인 설명 → 고객 적합성 필터 → 기업 후보 비교 → 선택하지 않은 대체 산업 제안 → 최종 결과/근거·데이터 시점 기록.
[권고] 관심 산업별 기업 후보는 최대 2~3개를 비교 화면에 제시할 수 있으나 적합 기업이 없으면 0개로 둔다. 기업 후보는 매수 지시와 구분한다. 종목선정 기준으로 수익성/성장성/재무건전성/밸류에이션/유동성/공시 위험/데이터 충분성/기존 포트폴리오 중복을 포함한다. 점수, 가중치, 추천·제외 컷오프는 데이터 검증 및 법적 범위 검토 전 [미확정]이다.
[확정] AI는 산업 전망 및 비교 설명을 생성할 수 있지만, 계산 확정값과 투자 적합성 제약의 진실 원천이 아니다. 가격·수익률·재무비율 계산은 검증 가능한 데이터·계산 엔진이 담당하고, 후보 필터는 규칙 기반 검증을 통과해야 한다.
5.2 데이터 소스 및 갱신 시점
[검증 필요] 데이터 공급 후보: 한국투자증권 KIS Developers(주식 시세·거래 관련 API), 금융감독원 OpenDART(공시 및 공시 재무정보), 공식 산업통계/기관 보고서(산업 전망). 실시간 시세 여부·시장별 지연·제공 권한·호출한도·상업적 재표시 허용·인증 요구는 각 공급자 최신 문서와 계약으로 확인한다.
[확정] 저장 항목: provider, endpoint, security_id/industry_id, observed_at(시장 기준 시각), retrieved_at(조회 시각), fiscal_period_end(재무제표 기준기간), filing_date(공시일), currency, unit, adjusted_flag, source_url, license_scope, expires_at/ttl, status(VERIFIED/STALE/UNAVAILABLE). 공시일과 데이터가 설명하는 실적 기준일은 다를 수 있다.
[권고] MVP는 요청 시 가격 조회, 공시·재무정보 캐시, 데이터 기한 초과 시 STALE와 추천 보류를 우선 구현한다. 업데이트 주기와 비용을 무조건 '실시간'으로 설계하지 않는다. OpenDART의 재무제표는 공시 기준 자료이지 초 단위 실시간 재무지표가 아니다.
6. 자금 원장·목표별 기간·보유 종목
[확정] assets[](보유자산), allocations[] (목적별 자금배정), monthly_allocations[] (월 잉여현금 배정), cashflow_events[] (날짜별 입출금)을 동일한 금액·시점·소유범위 규칙으로 연결한다. 목적 계정은 앱 내부의 논리적 바구니이며 별도 은행계좌 개설을 강제하지 않는다.
목적별 구분: 생활·비상 보호자금 / 특정 목표자금(목표 금액·필요일·현금화 가능일·우선순위) / 장기 투자 가능 자금 / 미배정 잔액. 한 자산의 목적배정 합계는 해당 자산의 보유액을 초과할 수 없다. 월 배정 총액도 월 배분 가능 재원을 초과할 수 없다. 목표기간이 짧거나 지급일 전에 현금화할 수 없으면 투자재원에서 제외한다.
[현행 충돌] 통합 시트 OPEN-04 및 F-10은 세부 보유내역·복수목표·건별대출을 현재 NOT_SUPPORTED/P2로 기록한다. 새 포트폴리오 요구인 '종목별 기존 보유내역 확인'은 무단으로 완료 처리할 수 없다. [권고] 기존 Q-024 보유 유무와 Q-023 평가총액은 유지하고, 사용자가 종목 중복 검토를 선택한 경우에만 별도의 holdings[] 구조화 입력 기능을 P1 후보로 승격할지 승인한다. 입력하지 않으면 실제 보유종목을 추측하지 않고 중복노출 평가는 NEEDS_INPUT/NOT_SUPPORTED로 표시한다.
보유종목 선택 입력 스키마 초안: instrument_id/ISIN 또는 표준 티커, 거래소·통화, 상품종류, 수량, 평가금액, 평가시점, 원가정보(선택), 계좌유형(선택), 정보출처(고객 입력/API), missing_status. ETF의 실질 기초자산/섹터 노출 중복 분석은 구성종목 자료의 기준일과 제공 범위를 별도 확인한다.
7. 세 가지 재무실행 전략 설계
PORT-01 안정 우선안: 재원 보호·비상유동성·의무지출 안전을 우선한다. PORT-02 현재 생활 유지안: 현재 생활 지출 수준에서 가능한 저축·투자 배분과 목표달성 시점을 보여준다. PORT-03 목표 달성 우선안: 고객이 허용한 지출 조정·기간·목표 조정 범위에서 목표 재원 확보를 우선한다. 어느 안도 무리한 위험 상향, 무단 지출감축, 임의 수익률로 부족을 감추지 않는다.
세 안은 같은 profile_version, evaluation_date, baseline, 세율·수익률 가정 버전, 투자 제약을 사용해 비교한다. 비교 항목: 월 가처분 여유, 비상금 보호 수준, 목표 충당률(성공확률로 표현 금지), 목표 도달 시점/부족액, 투자 가능 금액, 총 거래비용·예상 세금, 스트레스 상황의 최저 현금잔액, 각 안의 장단점·실행 난이도.
생성된 세 안이 동일하거나 실행 불가능할 수 있다. 이 경우 중복안 또는 INFEASIBLE/NEEDS_INPUT/REVIEW_REQUIRED를 명시하고 억지로 세 개를 만들지 않는다. 사용자는 미리보기 후 한 안을 명시적으로 채택한다. 채택 전/후 버전과 실적 기록을 보존한다.
8. 세후·비용 반영 모델
[확정] 총수익률만 보여주지 않고 가능한 범위에서 세금·매매수수료·ETF 총보수·환전 및 환율·계좌 관련 비용을 구분해 세후/비용 후 시나리오를 제공한다. 세법·계좌·상품 정보가 불충분하면 세후 금액을 확정하지 않고 '세전/비용 일부 미반영'이라고 표시한다.
[권고] 입력: 상품유형(국내주식/해외주식/국내상장 국내주식형 ETF/국내상장 기타 ETF/해외상장 ETF/예금·채권 등), 계좌유형(일반/ISA/연금저축/IRP 등), 과세연도, 거주자 상태·적용 가능 범위, 실현손익·배당/분배금, 취득가액, 수수료 및 환전비용, 연간 공제 사용 현황(불명 가능). 세금 계산은 규칙표 버전과 공식 출처를 요구한다.

* [확정] 산업 분석과 고객 적합성을 분리한다. 관심 산업 선택만으로 투자 비중을 늘리지 않는다.
* [확정] 원안의 고정 코어·위성 비율과 산업 수에 따른 균등배분은 최종 엔진에 사용하지 않는다.
* [확정] 자료가 부족하거나 부적합하면 후보 0개, 일부 결과 보류, 실행 불가능 판정을 정상 결과로 처리한다.
15.2 원문과 참고 파일이 충돌할 때
이 보완본과 v1.0의 합의 방향이 팀원 초기 Excel 예시보다 우선한다. Excel의 5개 자산군 비중은 legacy_reference로 보관한다. P1 주식/채권/현금성=10/70/20, P2=30/55/15, P3=50/40/10, P4=70/25/5, P5=85/10/5는 승인된 최종 배분 정책이 아니다. 기존 Excel의 0/10/20/30/40% 주식 내 위성 비중은 폐기된 로직의 기록으로만 남긴다.
원문이 인용한 통합 Q-ID, CALC-ID, G-ID, PORT-ID는 연결 단서다. 실제 코드나 시트를 수정하기 전에 대상의 최신 원장에서 존재·타입·활성 상태를 확인한다. 이 문서의 추가 필드명은 신규 계약 후보이며 기존 필드의 임의 변경 지시가 아니다.
15.3 지금 구현할 수 있는 것
입력 검증, 자금 원장, 재무현황 계산, 목표별 기간 연결, 미확정 정책에 대한 보류, 산업 자료의 출처 관리, 설명 템플릿, 계획 미리보기·채택·실적 기록부터 구현한다. 정량 정책이 없는 모듈은 계산을 조작해 완성하지 않고 REVIEW_REQUIRED와 필요한 정책 키를 반환한다. 이 상태에서도 재무진단과 자료 확인 화면은 사용할 수 있어야 한다.
16. 데이터 계약과 질문 이관
16.1 공통 데이터 규칙
[구현 제안] 모든 재무 입력에는 value, unit, scope, as_of, provenance, missing_status를 붙일 수 있는 공통 구조를 둔다. scope는 개인/가구를 구분하고 하나의 분석 실행 안에서 동일 기준을 사용한다. 계좌를 합칠 때 소유자 범위도 검증한다.
금액은 서버에서 Decimal로 계산하고 API에서는 원 단위 십진 문자열로 전달한다. 금리는 소수 문자열로 전달한다. 예: 금액 "3000000", 연 5%는 "0.05". 정수·소수 표시에 필요한 단위는 계약으로 고정한다. 수량과 외화는 원화 금액과 별도 필드로 저장한다. 프런트엔드에서 부동소수점으로 금융 계산을 확정하지 않는다.
0은 실제 0, null은 값이 없는 상태다. missing_status는 KNOWN / UNKNOWN / NOT_ASKED / NOT_APPLICABLE을 구분한다. 미입력을 0으로 바꾸지 않는다. 서버는 최대 금액·문자열 길이·날짜·배열 크기도 검증한다. 비율 분모가 0이면 해당 비율은 null이다.

아래 구조는 개발용 계약 초안이다. 기존 시스템의 field_key를 확인해 어댑터로 연결한다.

16.3 설문 이관 규칙
* 구 Q01~Q20은 간편, 구 Q21~Q40은 심화 추가 질문이라는 참고 구조다. 현재 활성 60개 질문을 이 체계로 전면 교체하지 않는다.
* 구 Q12 drawdown_reaction은 통합 loss_response와 의미 매핑한다. sell_some과 unknown 등 서로 없는 선택지를 임의 통합하지 말고 값의 출처와 원문 응답을 보존한다.
* 구 Q32 max_loss_tolerance는 신규 고객 설문에서 비활성화하는 방향이다. 기존 응답 기록은 삭제하지 않고 deprecated로 표시한다. 이 문항의 공백을 임의 손실률로 채우지 않는다.
* 구 Q33 loss_capacity와 통합 Q-122 생활영향을 의미 대조한다. 완전 일치가 확인되기 전에는 같은 enum으로 강제 변환하지 않는다.
* 구 40문항의 Q35 product_preferences와 산업선호 파일의 Q35 preferred_sectors는 서로 다른 데이터다. 독립 필드로 이관하고 화면 번호로 데이터 키를 만들지 않는다.
* EQ_TECH, EQ_BIGTECH, EQ_AI, EQ_ROBOT은 이름 유사성만으로 합치지 않는다. category_aliases에 원본 체계·대상 코드·의미·적용버전을 기록하고 확정된 별칭만 사용한다.
* Q20은 절세계좌 보유와 개설 의향을 한 문항에 섞고 있다. account_holdings와 account_interest로 분리해 후속 확인한다.
* Q31의 pension은 계좌 형태, stocks/bonds 등은 자산군이므로 단일 분류축으로 더하지 않는다. 연금계좌 안의 ETF도 종목과 자산군으로 나눠 기록한다.
이관표 필수 열은 source_schema_version, source_question_id, source_field, target_field, option_mapping, transform_rule, unresolved_reason이다. 충돌이 있는 응답은 NEEDS_INPUT으로 남긴다.
17. 공통 자금 원장과 계산 순서
17.1 결정론적 처리 파이프라인
1. 단위·소유범위·입력 형식과 질문 매핑을 검증한다.
2. 같은 기준일의 자산·부채·소득·지출을 정규화하고 합계와 내역을 대조한다.
3. 목표와 예정지출을 obligation_id로 연결해 중복을 제거한다.
4. 보호자금, 의무상환, 기한이 가까운 목표의 필요 현금과 현금화 가능일을 계산한다.
5. 보유자산 목적배정과 월별 신규 배분을 각각 생성한다.
6. 투자 가능 금액과 시점을 산출한다.
7. 위험선호와 투자 여력·기간 제약을 독립 평가한다.
8. 동일 조건에서 PORT-01~03을 계산하고 가능 여부를 판정한다.
9. 투자 구성·상품 후보·산업 분석을 각자의 상태와 함께 반환한다.
10. 검증된 수치와 근거만 설명에 전달하고 고객의 명시적 채택을 기다린다.
17.2 기초 계산식
known_assets = 부동산 및 회수가능 보증금 + 현금성자산 + 금융투자자산 + 확인된 기타자산. 기타자산 미입력은 부분 집계로 표시한다.
net_worth = known_assets - total_debt. 순자산이 곧 투자 가능 현금은 아니다. 임차보증금·연금·매각 전 부동산은 현금화 시점을 별도 확인한다.
monthly_surplus = monthly_income - monthly_expenses - monthly_debt_payment. 생활비는 대출 원리금 제외 기준이다. 중복 포함이 의심되면 입력을 확인한다. 음수는 현금흐름 적자로 보존한다. 신규 투자 배분 한도는 max(0, monthly_surplus) 이하이며 목표·보호금 충당 후 다시 제한한다.
emergency_target = reserve_base_monthly × reserve_months. reserve_months는 검증된 정책값이 필요하다. reserve_base_monthly가 필수생활비만 포함하는지 의무상환도 포함하는지 정책에 명시한다. [구현 제안] 필수생활비와 불가피한 의무상환을 보호하려면 합산 기초를 사용할 수 있다. 이는 기존 식의 자동 변경이 아니라 정책별 비교·검산 대상이다.
immediate_emergency_gap = max(0, emergency_target - 비상용으로 배정된 즉시 인출 가능 자금). 다른 목표에 배정된 현금을 다시 비상금으로 세지 않는다. 예금 만기가 지급일 이후라면 즉시 유동성에 포함하지 않는다.
new_investable_lump_sum = 장기 투자용으로 확정 배정할 수 있는 자금의 합계. 단순히 총자산에서 총부채와 모든 목표금액을 일괄 차감하지 않는다. 실제 상환일·목표일과 기존 배정을 고려해 원장으로 산출한다. 기존 투자자산의 유지분과 신규 투자 가능 현금도 별도 표시한다.
17.3 중복과 음수 방지
각 plan_id와 기준시점에서 sum(allocations.amount for asset_id) ≤ asset.value_krw. 담보·출금제한 금액은 사용 가능액 계산에서 제외한다. allocations는 음수가 될 수 없다. 한 자산을 여러 목적에 나눌 때도 원래 asset_id를 유지한다.
월별 배분합 + 월 미배정 잔액 = 해당 월 배분 가능 신규 재원. 현재 잔액과 미래 저축을 같은 시점의 원금으로 더하지 않는다. 목표 바구니로의 이체는 소비가 아니며 전체 순자산에서 다시 빼지 않는다. 목표의 실제 지급일에만 해당 지급을 반영한다.
Q09 예정 목돈과 goals[]에 같은 이사비가 있으면 하나의 obligation_id로 연결한다. 중복인지 확인되지 않으면 조용히 합치거나 둘 다 차감하지 말고 NEEDS_INPUT을 반환한다.
17.4 날짜별 현금흐름
cash_balance(t) = opening_cash + t까지 실제 유입 - t까지 실제 유출. 동일 날짜 사건의 순서가 필요하면 타임스탬프 또는 보수적인 결제 순서 정책을 사용한다. 월말 흑자여도 월중 지급일에 잔액이 음수면 해당 계획은 INFEASIBLE 또는 조정이 필요한 상태다.
일시납 목표의 종료월과 월 납입일·월말 평가일을 구분한다. 중도인출 제한·결제일·환전기간을 반영하지 못하면 지급 가능일을 확정하지 않는다.
18. 위험성향과 투자 여력을 연결하는 의사결정
18.1 결과 필드 분리
risk_preference_class는 P1~P5 선호유형이다. preference_policy_version과 사용 응답을 함께 보존한다. 점수표가 없으면 null과 REVIEW_REQUIRED를 반환한다. 행동 질문 하나로 5개 유형을 임의 배정하지 않는다.
investment_capacity는 확인된 투자 가능액, 월 투자 여력, 보호금 부족액, 사용기간, 현금흐름 스트레스 결과, 필수지출 영향, 설명 근거를 보관한다. 고객의 인격·능력 평가 점수로 노출하지 않는다.
suitability_decision은 이 고객의 이 자금 목적·기간에 대해 이 후보 구성이 가능한지를 판정한다. 선호유형을 덮어쓰지 않으며, 같은 고객의 단기 목표자금과 장기 투자자금은 서로 다른 실행 제약을 가질 수 있다.
18.2 규칙 적용 순서
* 입력 부족이면 해당 평가만 NEEDS_INPUT. 기초 재무현황처럼 계산 가능한 결과는 유지한다.
* 생활비·의무상환·사용일이 정해진 목표자금은 먼저 확보한다. 보호금 부족을 투자수익으로 해결했다고 가정하지 않는다.
* 투자재원이 없으면 신규 투자금은 0원이다. 재무계획과 실행 체크리스트는 계속 제공한다.
* 투자재원이 있어도 상품의 사용가능 시점, 손실 영향, 유동성, 이해도, 제외 조건을 검증한다.
* 수치 정책이 없으면 REVIEW_REQUIRED. 과거 예시 비중이나 LLM 응답을 정책으로 채우지 않는다.
* 정량·비정량 제약을 모두 통과한 경우에만 해당 제안의 ALLOWED를 반환한다. 고객 동의 체크박스는 차단 조건을 해제하지 않는다.
18.3 스트레스 손실 검증
[구현 제안] 상품·자산군별 stress_scenarios에 가격, 금리, 환율, 신용, 유동성 충격을 명시한다. loss_budget은 생활·상환·보호금·목표자금을 유지할 수 있는 범위에서 별도 검증한 정책으로 산정한다. loss_budget과 stress_scenarios가 없으면 스트레스 적합성을 판정하지 않는다.
stress_loss_s = max(0, 평가기준액 - 시나리오 s의 비용 후 평가액). worst_stress_loss = max(stress_loss_s). 숫자가 산정되더라도 이를 최대 가능 손실이나 손실보장 한도라고 부르지 않는다. 최악 상황 전체를 포괄한다는 뜻이 아니다.
통과 조건은 정책이 정의한 스트레스 손실 제한, 날짜별 지급 가능성, 상품 제약을 함께 만족하는 것이다. 고객이 P5를 선호해도 보호자금이 필요한 경우 선호=P5를 유지한 채 실행 금액·구성 조정 또는 보류를 설명한다. 서로 다른 척도인 P등급과 현금여력을 단순 평균 내지 않는다.
19. 목표별 투자 구성과 기존 보유 내역
19.1 구성 생성
[구현 제안] 목표별로 투자기간, 필요한 현금화 시점, 보호금 여부, 허용상품, 고객의 선호유형을 묶은 mandate를 만든다. mandate는 실제 주문 권한이 아니라 앱의 구성 제약이다.
생성기는 검증된 policy_bundle과 candidate_universe를 입력받아 자산군 목표 구성, 후보 구성, 미배정 잔액, 제약 위반 사유를 반환한다. 초기에는 승인된 구성 템플릿 선택과 제약 검증부터 구현한다. 근거 없는 기대수익률 최적화나 LLM이 생성한 비중을 사용하지 않는다.
중립형이라는 이유만으로 주식 50%를 최종 적용하지 않는다. 같은 P3라도 1년 후 필요한 돈과 장기자금의 구성이 달라질 수 있다. 단기라는 이유만으로 모든 채권·채권 ETF를 안전자산으로 취급하지 않는다. 만기·듀레이션·환율·신용·매도 가능성을 검사한다.
금액 배분에서 반올림 잔액은 정책에 따라 미배정 현금으로 둔다. 최소 거래단위와 가격이 확인되지 않았다면 수량이나 주문금액을 제안하지 않는다. 원 단위 합계는 정확히 원장 재원과 일치해야 한다.
19.2 보유 내역 확인
보유평가총액과 holdings[] 합계를 대조한다. 내역이 일부만 입력되면 coverage를 표시하고 누락분은 unknown_exposure로 유지한다. 부분 내역으로 전체 집중도가 낮다고 판정하지 않는다.
ETF의 실질 노출과 개별주식 중복은 구성종목 자료가 있는 범위에서만 계산한다. 합성·재간접 ETF나 공개 범위가 불충분한 경우 exposure_status를 제한한다. 오래된 구성내역을 현재 구성으로 표시하지 않는다.
신규 납입으로 조정하는 대안과 기존 자산을 매도하는 대안을 구분한다. 매도 여부를 고객이 허용하지 않았거나 세금·비용이 불명확하면 매도 없이 가능한 구성만 제시하거나 조정을 보류한다. 기존 보유내역 기능의 우선순위는 v1.0의 미결정 상태를 유지한다. 스키마 설계가 완료되어도 해당 기능 출시 완료로 기록하지 않는다.
20. 산업 분석·기업 후보와 데이터 신뢰성
20.1 산업 분석 출력
IndustryAssessment에는 industry_id, assessment_as_of, positive_factors[], negative_factors[], uncertain_factors[], evidence_refs[], data_coverage, freshness_status를 둔다. 산업에 하나의 낙관 점수만 부여하지 않는다. 전망과 관측 사실을 구분하고 전망에는 기간과 가정을 기록한다.
고객 적합성은 CandidateAssessment에 별도로 기록한다. instrument_id, eligibility_decision, reason_codes[], exclusion_matches[], existing_exposure_status, liquidity_check, cost_tax_status, evidence_refs[]를 포함한다.
순서는 데이터 검증 → 제외·구조·유동성 등 필수 필터 → 고객 적합성 → 비교 지표 산출 → 근거 설명이다. 긍정적인 산업 평가가 차단된 종목을 복원할 수 없다. 선호하지 않은 대체 산업도 같은 검증 경로를 거친다. 대체 산업 편입을 강제하지 않는다.
20.2 기업 비교 지표
수익성·성장·재무건전성·밸류에이션·유동성·공시 위험을 비교할 수 있도록 계산을 분리한다. 지표의 분모가 0 또는 음수라 의미가 없으면 null과 사유를 반환한다. 적자기업 PER을 0으로 만들어 저평가로 분류하지 않는다.
같은 회계기간·연결/별도·통화·단위 기준을 맞춘다. 공시 정정은 기존 사실을 조용히 덮어쓰지 않고 새 버전으로 연결한다. 비교 점수 가중치·컷오프가 없으면 정렬 근거를 임의 생성하지 않는다. 사실 비교는 가능하되 매수 순위를 확정하지 않는다.
기업 후보는 적합 자료가 있는 경우에만 최대 2~3개 비교할 수 있다. 0개를 정상 처리하고, 비교 후보가 실제 편입 종목이라는 인상을 주지 않는다. 기업 후보 데이터와 실제 거래 가능한 검증 상품 카탈로그의 상태를 구분한다.
20.3 공급자와 시점
KIS Developers는 시세·시장 데이터 공급 후보이며 OpenDART는 공시와 정기보고서 재무정보 공급 후보다. 본 문서에서는 인증·실제 호출·사용권 계약을 검증하지 않았다. 실시간 수신과 고객 화면 재표시는 별개의 권한으로 확인한다.
가격 observed_at, 수집 retrieved_at, 공시 filing_date, 실적 fiscal_period_end를 별도 저장한다. source_url, provider, endpoint, response_hash, schema_version, license_scope, ttl, status도 기록한다. 분석 당시 사용한 data_snapshot_id로 재현할 수 있어야 한다.
최신성 기준은 데이터 종류와 시장 영업일 기준으로 정책화한다. 휴장일의 마지막 종가를 단순히 오래됐다는 이유만으로 오류 처리하지 않는다. 반대로 재무공시가 존재한다는 이유로 시세까지 최신으로 판정하지 않는다. 상태는 VERIFIED / STALE / UNAVAILABLE로 구분한다.
공식 자료에서 OpenDART의 공시검색과 정기보고서 재무정보 API 제공 범위를 확인했다. [검증 필요] KIS 포털 검색에는 국내주식 재무분석 API 일부의 2026-11-11 종료 예정 안내가 노출되지만 본문 재조회는 완료되지 않았다. 적용 API 목록·시행시각을 직접 확인하기 전 의존성을 확정하지 않는다. 재무정보 수집을 한 증권사 분석 API에 고정하지 않고 공급자 어댑터로 분리한다.
API 키는 서버 비밀값으로 관리한다. rate limit, timeout, 재시도 상한, backoff, 요청 중복 제거, 캐시를 둔다. 공급자 장애 시 마지막 정상 데이터와 오래된 상태를 함께 표시한다. 최신 자료가 필요한 후보 추천은 보류하고 기초 재무진단은 계속 제공한다.
21. 세후·비용 후 시뮬레이션
21.1 회계 흐름
[구현 제안] 각 기간의 기초 평가액 + 납입 - 인출 + 가격손익 + 현금분배 - 직접 비용 - 과세사건별 세금 = 기말 평가액으로 정의한다. 배당·이자가 가격에 포함된 총수익 데이터인지 확인해 중복 가산하지 않는다.
연 수익률을 월로 바꿀 때 effective_annual인지 nominal_annual인지 명시한다. 유효 연 수익률이면 월률=(1+연률)^(1/12)-1이다. Decimal의 정밀도·거듭제곱과 최종 반올림 규칙을 테스트한다. 확정되지 않은 미래수익률은 정책에 있는 시나리오 가정으로만 사용하고 예상 확정수익으로 표시하지 않는다.
0% 수익 가정에서 goal_gap=max(0, target_amount-assigned_initial_funding), required_monthly=goal_gap/remaining_payment_count. 납입 횟수는 실제 일정으로 계산한다. 목표일이 과거거나 남은 납입 횟수가 0이면 나누지 않고 즉시 충당 여부를 판정한다.
실질 목표금액은 기준일·물가 가정을 기록하고 미래 명목 목표로 변환할지 정한다. 이미 미래 금액으로 입력한 목표에 물가를 다시 적용하지 않는다. 목표 충당률을 목표 달성 확률로 바꾸지 않는다.
21.2 비용·세금 규칙
매매수수료, 환전 비용, 매수·매도 스프레드, 상품 보수, 계좌 비용은 적용 시점과 이미 반영된 항목을 구분한다. ETF NAV나 보수 차감 후 수익률을 사용할 때 총보수를 다시 빼지 않는다.
세금은 instrument_tax_class, account_type, tax_year, residency, realized_event, acquisition_cost, distribution, applicable_deductions, foreign_tax 등 확인된 정보로 판정한다. 상품명에 ETF가 들어간다는 이유로 같은 세율을 쓰지 않는다. 미실현 평가차익에 실현세금을 무조건 차감하지 않는다.
TaxRule은 effective_from, effective_to, jurisdiction, source_url, verified_at, reviewer, rule_version을 갖는다. 세율·한도·가입자격·손익통산은 검증 전 빈 정책으로 유지한다. 국세청 공식 자료는 금융소득 원천징수와 국외주식 신고의 출발 자료이며, 모든 상품·계좌 세제를 검증한 상태를 의미하지 않는다.
필요 데이터가 없으면 tax_status=NEEDS_INPUT 또는 REVIEW_REQUIRED, net_after_tax=null을 반환한다. 세금이 0원인 경우와 세금 계산 불가를 구분한다. 비용 일부만 확인되면 confirmed_costs와 unmodeled_costs를 함께 내보낸다. 세전 결과는 계속 볼 수 있게 한다.
22. 세 가지 계획 비교와 고객 화면
22.1 비교 조건
PORT-01은 보호·안전한 자금흐름을 우선한다. PORT-02는 현재 생활비를 유지한다. PORT-03은 고객이 허용한 생활비 조정·목표 조정 범위에서 목표 재원 확보를 우선한다. 정확한 월 배분 비율은 policy_bundle이 정의하며, 없으면 REVIEW_REQUIRED다.
planning_preferences에는 조정 가능한 지출 항목, 조정 한도, 최소 생활 여유, 목표기간 연장 허용, 목표금액 조정 허용을 둔다. 고객이 허용하지 않은 지출 감소나 소득 증가를 계획에 넣지 않는다. 필수생활비·의무상환을 목표 달성을 위해 임의 감축하지 않는다.
세 안은 동일 profile_version, evaluation_date, data_snapshot_id, 경제 가정·세금·비용 버전을 쓴다. 전략 때문에 발생한 차이는 별도 표시한다. 수익률만 다르게 설정해 한 안을 유리하게 만들지 않는다.
22.2 계획 카드 구성
카드 상단에 계획명과 고객에게 미치는 핵심 차이를 적는다. 월 생활 여유, 보호자금 충족 수준, 목표별 배정액·부족액·도달시점, 신규 투자 가능액, 기존 투자 유지액, 비용·세금 상태, 주요 제약을 보여준다.
자산 목적별 차트는 보호금·목표금·장기투자·미배정으로 구성한다. 투자금 구성 차트는 그중 투자 범위 내부의 자산군 구성을 보여준다. 두 차트 금액을 더하지 않는다. 기존 보유자산 구성과 새 제안은 별도 비교한다. 투자금 내부 현금성 배정은 비상자금과 별도 asset allocation으로 연결해 이중 계상하지 않는다.
추천 가능 여부, 누락 입력, 자료 기준일, 적용 가정을 카드에서 확인할 수 있어야 한다. ‘투자 여력이 부족한 사람’ 같은 표현 대신 ‘이번 목표에 우선 확보할 자금’과 구체적인 금액·기한을 설명한다.
22.3 채택과 사후 점검
미리보기 생성은 실행 지시가 아니다. 명시적 채택은 사용자 조작으로만 발생한다. 채택 시 run_id, plan_id, profile_version, rule_version, data_snapshot_id를 고정한다. 채택 이후에는 변경을 새 버전으로 남긴다.
실행 화면에는 이번 달 보호금 확보, 목표 적립, 부채 상환, 확인해야 할 정보와 완료 상태를 연결한다. 실제 주문·송금은 현재 범위에 포함하지 않는다. 한 달 후에는 실제 소득·지출·잔액·진행률과 계획을 비교하고 입력 변경에 따라 재계산한다. 가상 한 달 후 시연은 실제 한 달 경과와 구분해 표시한다.
23. API·저장 구조·AI 계약
23.1 기존 구현과 신규 계약
참고 아키텍처 v2.0은 Next.js/React/TypeScript, FastAPI/Pydantic, Python Decimal 기반의 점진 확장을 제안한다. 이 작업에서는 저장소의 현재 코드를 재검사하지 않았다. 실제 개발 시작 시 AGENTS.md, 현재 디렉터리, 기존 /api/calculate 계약과 테스트를 먼저 확인한다. 문서만 보고 이미 구현됐다고 판단하지 않는다.
신규 제안 API: POST /api/v1/diagnoses, POST /api/v1/portfolios, POST /api/v1/plans/compare, POST /api/v1/plans/{id}/adopt, POST /api/v1/reviews, POST /api/v1/analyze. 기존 API를 덮어쓰지 않고 어댑터 또는 버전 엔드포인트로 확장한다.

status는 데이터·계산의 완전성(insufficient_data / provisional / complete), decision은 해당 추천의 가능 여부다. data freshness, tax status, legal scope는 독립 필드다. 숫자 계산이 complete여도 추천이 REVIEW_REQUIRED일 수 있다. complete는 앱 테스트 통과나 법적 운영 가능을 의미하지 않는다.
잘못된 타입·음수 입력·중복 ID는 422로 반환한다. 유효한 요청에서 정보 부족·부적합·미확정 정책이 발생한 경우에는 계산 가능한 결과와 상태를 정상 분석 응답에 담는다. 공급자 장애는 해당 데이터/후보 모듈의 상태로 전달한다. 무조건 전체 결과를 0으로 초기화하지 않는다.
동일 입력·정책·데이터 스냅샷의 결정론적 결과는 같아야 한다. adopt에는 Idempotency-Key와 예상 plan_version을 사용해 중복 채택·동시 변경을 방지한다. 이전 버전의 미리보기를 최신 계획으로 몰래 채택하지 않는다.
23.3 저장 모델
case → profile_version → analysis_run → plans → adoption → actions/reviews를 연결한다. 각 analysis_run에 policy_bundle_id와 data_snapshot_id를 고정한다. assets, debts, goals, holdings는 프로필 버전에 종속한다. allocations는 plan_id에 종속하고 외래키로 asset·goal을 참조한다. 같은 plan_id의 원장 배분을 트랜잭션으로 검증한다.
상품·산업 자료는 instrument_id, industry_id, source_snapshot_id, valid_time, retrieved_time을 보존한다. 수정·삭제 정책은 원문 로그를 무기한 저장한다는 뜻이 아니며 실제 개인정보 보존정책과 맞춘다. 민감한 재무 원문과 API 비밀값을 일반 로그에 남기지 않는다.
23.4 AI 비용과 검증
간편 진단·계산·정적 설명 경로의 LLM 호출은 0회로 구현한다. 심화 설명·산업 분석 요청에서만 선택 호출한다. API 키가 없어도 기본 재무진단과 미확정 상태 표시가 동작해야 한다.
LLM 입력은 검증된 facts, evidence_refs, reason_codes와 필요한 최소 고객 맥락이다. 출력은 narrative, used_fact_ids, used_evidence_refs, uncertainty로 구조화한다. LLM이 계산·적합성·법적 상태를 변경하지 못하게 한다.
금액·퍼센트·기간·기준일이 사실과 일치하는지 검증한다. 설명의 숫자는 가능한 한 fact_id 템플릿으로 렌더링한다. 검증 실패는 정적 설명으로 대체한다. 외부 문서의 명령문은 분석 자료로만 취급한다. 개인정보를 제거한 동일 근거·정책 해시로 캐시하며 서로 다른 고객의 재무 설명을 섞지 않는다.
24. 법적 범위와 출시 판단의 분리
이 문서는 법률의견서가 아니다. 금융위원회 공식 안내는 개별 투자자문과 유사투자자문업의 업무범위를 구분한다. 개인별 상품·종목·비중 제안의 실제 운영 형태는 등록·제휴·보수·서비스 구조 등을 포함해 별도 검토한다. ‘교육용’ 문구만 추가해 적법성을 확정하지 않는다.
[구현 제안] 개발환경은 가상 고객·픽스처로 계산과 인터페이스를 구현한다. recommendation_scope와 legal_review_status는 계산 상태와 분리한다. 이 문서 작성만으로 실고객 개인화 종목 추천을 운영 가능으로 전환하지 않는다. 법률 검토 대기 때문에 자금 원장·재무진단·화면 개발까지 멈출 필요는 없다.
정량 추천 정책, 실제 상품 데이터 사용권, 세금 규칙, 실고객 데이터 처리 범위의 미결정 항목을 각각 별도 이슈로 관리한다. 개발자가 임의로 값을 채워 완료 표시하지 않는다.
25. 독립 검산용 예시와 필수 테스트
25.1 숫자 예시의 조건
다음은 단위·중복 배정 검증을 위한 가상 픽스처다. 비상금 6개월 등은 실제 고객 정책이나 신규 합의가 아니다. 테스트 실행 시 fixture_only=true로 표시하고 운영 정책과 분리한다.
기준일 현금 20,000,000원, 부동산·기타·기존 투자자산은 확인된 0원, 부채잔액 10,000,000원. 세후 월소득 3,000,000원, 대출 원리금 제외 월생활비 1,800,000원, 그중 필수생활비 1,200,000원, 월 의무상환 300,000원.
예시 보호금 기초는 필수생활비+의무상환=1,500,000원, 가상 reserve_months=6, 보호금 목표=9,000,000원이다. 12개월 뒤 쓸 목표자금 6,000,000원을 현재 현금에서 별도 확보한다. 이 목표와 예정지출은 같은 obligation_id로 등록한다.
기대 결과: 총자산 20,000,000원, 순자산 10,000,000원, 월 잉여현금 900,000원. 현금 목적배정은 보호금 9,000,000 + 목표금 6,000,000 + 장기투자 배정 후보 5,000,000 = 20,000,000원이다. 부채잔액 10,000,000원을 현금에서 다시 일괄 차감하지 않는다. 향후 상환은 지급일 현금흐름에 반영한다.
목표금은 이미 충당했으므로 이 목표의 현재 부족액은 0원이다. 다만 향후 주거계획 등 다른 미확인 의무가 있으면 추가 입력이 필요하다. 장기투자 배정 후보 5,000,000원은 특정 상품 추천 승인을 의미하지 않는다. 분류·배분 정책이 없으면 투자성향과 최종 비중은 null/REVIEW_REQUIRED다.
25.2 테스트와 기대 결과
* AT01: 위 픽스처를 계산하면 월 잉여금 900,000원·원장 잔액 0원이 일치한다.
* AT02: 현금 20,000,000원에 목적배정 21,000,000원을 요청하면 초과 배정을 거절한다.
* AT03: 동일 이사비를 예정지출과 목표에 등록하면 연결된 obligation_id 기준으로 한 번만 반영한다.
* AT04: 소득 0원은 상환비율 null이며 현금흐름 적자를 0으로 숨기지 않는다.
* AT05: 기타자산 미입력과 확인된 0원을 구분하고 총자산의 부분 집계 상태가 달라진다.
* AT06: 구 Q32 비활성화 후에도 통합 Q-032와 Q-122가 존재하고 데이터가 보존된다.
* AT07: 산업 0개는 허용, 4개·중복·미등록 ID는 입력 오류다.
* AT08: 선호산업과 제외상품이 충돌하면 제외 조건을 우선하며 후보 0개도 정상이다.
* AT09: 산업 분석이 긍정이어도 고객의 사용기간·생활영향 제약을 위반하면 편입을 보류한다.
* AT10: P5 선호 픽스처에서도 보호금과 단기 목표금은 주식 편입 재원에 들어가지 않는다. 분류 입력은 운영 분류기가 아니라 테스트 전용이다.
* AT11: 정책표가 없으면 점수·최종 비중·세율을 생성하지 않고 missing_policy_keys를 반환한다.
* AT12: holdings 일부 미입력은 중복노출 평가 불완전이며 분산 적정 판정으로 둔갑하지 않는다.
* AT13: 총자산에 holdings를 다시 합산하지 않는다. 연금계좌와 내부 ETF도 중복 집계하지 않는다.
* AT14: 정책 기준을 넘은 시세는 STALE, 공시누락은 UNAVAILABLE이며 후보 추천을 제한한다.
* AT15: 가격 시각·공시일·회계기간·조회시각이 각각 보존된다. 정정공시는 새 스냅샷을 만든다.
* AT16: 세금 데이터가 없으면 세후 금액은 null이다. 확인된 0원 세금과 구분한다.
* AT17: 보수 차감 후 수익률에 총보수를 다시 빼지 않는다. 배당 포함 수익률에 배당을 다시 더하지 않는다.
* AT18: 같은 기준일·가정으로 3안을 비교하며 동일안은 중복으로 표시한다. 실행 불가능안을 억지로 가능하게 만들지 않는다.
* AT19: 월말 흑자여도 월중 지급일 부족이 발생하면 현금흐름 제약이 드러난다.
* AT20: 원 단위 반올림 후 구성합계와 재원은 정확히 일치하고 잔액은 현금으로 남는다.
* AT21: LLM의 금액·기간·추천상태 불일치는 정적 설명으로 대체한다. 계산 경로의 LLM 호출 수는 0이다.
* AT22: 명시적 채택 전에는 실행 계획을 활성화하지 않는다. 동일 채택 요청 재전송은 중복 이력을 만들지 않는다.
* AT23: 프로필 변경 후 과거 미리보기 채택은 버전 충돌을 반환하며 기존 기록을 덮어쓰지 않는다.
* AT24: 새 계획·실적 비교는 이전 채택 버전을 보존하고 가상 점검과 실제 실적을 구분한다.
이 목록은 테스트 명세다. 현재 앱에서 실행·통과한 결과가 아니다. 개발자는 계산 단위 테스트, API 계약 테스트, 대표 사용자 경로 E2E로 나누어 실행 증거를 기록한다.
26. 구현 순서와 산출물
26.1 1차: 기존 구조 확인과 재무 엔진
현재 저장소의 지침·엔드포인트·테스트를 확인하고 기존 field_key와 신규 계약의 대응표를 작성한다. 단위·누락·합계 검증, 자금 원장, 목표·예정지출 중복 제거, 날짜별 지급 가능성, 미확정 정책 상태를 구현한다. 산출물은 영향도 표, 입력·출력 스키마, 계산 모듈, AT01~06·AT11·AT13·AT19~20의 실행 결과다.
26.2 2차: 의사결정과 계획 비교
선호유형·투자여력·적합성 결과를 분리한다. PORT-01~03의 정책 인터페이스, 고객이 허용한 조정 범위, 비교 화면, 명시적 채택을 연결한다. 미확정 수치에는 상태와 사유를 사용한다. 산출물은 decision log, 계획 비교 API, 원장 기반 차트, 채택 버전 테스트다.
26.3 3차: 외부 데이터·산업·기존 보유
공급자 어댑터·자료 스냅샷·카탈로그·제외 필터를 구현한다. 먼저 가상 응답으로 타임아웃·지연·누락·정정공시를 검사한다. 실제 호출 권한이 준비되면 읽기 전용 데이터 연동을 검증한다. 보유내역은 원문의 우선순위 결정을 확인한 뒤 구현 범위를 적용한다.
26.4 4차: 세후 비교·설명·사후 점검
검증된 범위의 비용·세금만 연결하고 미지원 범위를 표시한다. 설명은 템플릿부터 완성하고 LLM은 선택 기능으로 추가한다. 실제 월 실적 입력과 재설계를 연결한다. 마지막으로 핵심 E2E와 개인정보·출처·법적 범위 상태를 점검한다.
27. 다른 대화에 붙여 넣을 개발 시작 지시문
dion / dion의 재무설계·투자 포트폴리오 개발을 이어 진행한다.


첨부한 「재무설계·투자 포트폴리오 설계 기준서」의 v1.0 제0~14절과 개발 인계 보완본 v1.1 제15~28절을 읽어라. 기존 합의, 구현 제안, 검증 필요 정책값을 구분하라. 문서만으로 현재 코드가 구현되었다고 간주하지 마라.


먼저 현재 작업 폴더, AGENTS.md, git 상태, 기존 API·스키마·계산 엔진·테스트를 확인하라. 현재 질문 원장과 데이터 계약이 접근 가능하면 Q-ID 및 필드를 대조하라. 접근할 수 없으면 그 부분만 미확인으로 남기고 독립 가능한 계약·자금 계산부터 진행하라.


기존의 동작하는 기능과 API 계약을 보존하며 작은 기능 구현 → 실제 실행 → 결과 검사 → 문제 수정 순서로 개발하라. 저장소 전체를 새로 만들거나 기술 스택을 일괄 교체하지 마라.


첫 작업은 단위·누락·범위 검증, 자금 원장, 목표와 예정지출 중복 제거, 날짜별 지급 가능성, 정책 미확정 상태를 하나의 수직 기능으로 구현하는 것이다. 스키마, 순수 계산, API, 최소 결과 화면을 연결하고 AT01~06·AT11·AT13·AT19~20을 검증하라. 검사 실패는 고치고 계속하라.


P1~P5의 선호유형과 PORT-01~03 실행전략을 분리하라. 구 Q32 비활성화가 통합 Q-032 대출잔액이나 Q-122 생활영향 삭제로 이어지면 안 된다. 상품 제외정보를 산업 선호로 덮어쓰지 마라. 원안의 고정 코어·위성·산업 균등배분 로직을 되살리지 마라.


금액은 Decimal로 계산하고 JSON에서는 십진 문자열을 사용하라. 투자 가능액, 기존 보유액, 보호금, 목표금, 미래 월저축을 중복 집계하지 마라. holdings는 자산의 내역이며 추가 자산이 아니다.


위험 분류 가중치·허용 상한·최종 자산군 비중·스트레스 손실·종목점수·세율은 근거 없이 만들지 마라. 정책이 없으면 REVIEW_REQUIRED와 필요한 policy key를 반환하되 계산 가능한 재무결과는 제공하라. 숫자 픽스처는 fixture_only로 격리하라.


산업전망과 고객 적합성을 별도 계산하라. API·공시의 출처와 시점을 보존하고 고객 제외조건과 적합성을 통과한 후보만 비교하라. 실제 상품과 데이터 사용권이 미검증이면 검증 완료로 기록하지 마라.


간편 진단은 LLM 없이 동작하게 하라. AI는 검증된 수치·근거 설명에 사용하고 계산·제약·채택을 변경하지 못하게 하라. 실제 주문·송금은 현재 범위에 포함하지 않는다.


작업 결과는 변경 파일, 바뀐 동작, 검산·테스트 결과, 남은 미확정 정책, 다음 구현 단위로 보고하라. 설계 완료·앱 실행·실제 데이터 연동·운영 승인 상태를 분리하라. 별도로 요청받지 않은 배포·원격 업로드·공유는 수행하지 마라.

데스크톱은 A·B를 나란히, C를 그 아래, D 세 카드를 같은 행에 배치한다. 좁은 화면은 A→B→C→D 순서로 한 열에 배치하고 계획 선택·비교 표를 제공한다. 가로 스크롤만 해야 핵심 금액이나 채택 버튼이 보이는 구조는 피한다. 시각 순서와 키보드·스크린리더 읽기 순서를 맞춘다.
29.2 결과 기준의 분리
* A와 B는 현재 보유현황이다. 제안 비중을 현재 보유액에 반영하지 않는다. B는 A의 부분집합이며 두 합계를 더하지 않는다.
* C의 현재 준비금에는 이미 존재하고 해당 목표에 배정된 재원만 반영한다. 향후 월 납입과 미래 수익은 예상 재원으로 따로 표시한다.
* D는 동일 고객정보·기준일·경제 가정·자료 스냅샷에서 만든 계획 비교다. 채택 전에는 모두 미리보기다.
* 보유액 단위인 원과 월 납입 단위인 원/월을 같은 원형 차트나 합계에 섞지 않는다.
* 고객의 P1~P5 선호유형은 별도 표시한다. 세 실행계획을 세 위험등급으로 이름 붙이지 않는다.

	기존 유지 납입이 목표/투자 배정에 이미 포함됐으면 다시 더하지 않음. 정책이 없으면 배분행만 ‘—’
	VIEW-D04
	보호금·목표 준비
	보호금 목표/현재 배정/부족, 목표 준비금/부족/도달시점
	보호기간·배분정책이 미정이면 해당 결과만 보류
	VIEW-D05
	투자재원
	신규 일시 투자 후보액, 월 신규 투자액, 기존 투자 유지액을 각각 표시
	일시금과 원/월 합산 금지. 확인된 0원과 계산 불가 구분
	VIEW-D06
	실행 부담·제약
	현재 대비 생활비 변화, 목표기한·규모 변경, 지급일 부족금액·날짜, 적용 조건
	확인된 차이만 표시. 실행 불가·중복안도 정상 결과로 노출
	VIEW-D07
	비용·세금 상태
	확인된 비용·추정 세금·미반영 항목·기준기간
	미계산은 0원이 아니라 ‘미확인’. 세후 결과가 없으면 세전/비용 반영 범위 표시
	VIEW-D08
	계획 확인·선택
	‘자세히 보기’와 ‘이 계획으로 실행하기’ 버튼 분리, 채택 상태
	미리보기 클릭으로 채택하지 않음. 보류 조건과 확인 경로를 해당 버튼에 연결
	

월 자금 배분은 의무상환과 생활비를 차감한 예산에서 생성한다. 이미 차감한 의무상환은 신규 배정으로 다시 빼지 않는다. 선택적 추가상환은 의무상환과 구분한다. 기존 납입이 다른 목적에 반드시 유지되는지 확인하고 동일 현금흐름이 여러 행에 중복 집계되지 않게 한다. 배분 후 남는 금액과 생활비 예산, 배분 전 월 잉여현금은 서로 다른 숫자다.
정책 부재로 세 계획 수치가 없으면 카드별 수치를 억지로 생성하지 않는다. ‘공통 재무현황’과 ‘계획별 배분 기준 확인 필요’를 분리 표시한다. 서로 같은 결과가 나온 카드도 차이를 꾸미지 않고 동일 결과임을 알린다.

32. 숫자·차트·설명·상태의 공통 출력 규칙
32.1 표시 규칙
항목
	규칙
	금액·단위
	기본 통화 KRW. 화면은 원/만원 축약을 사용할 수 있으나 상세표에 정확한 원 단위 제공. 월 금액은 반드시 원/월 또는 만원/월 표시
	원값과 반올림
	계산 원값·저장값은 기존 Decimal 계약 유지. 차트 라벨의 반올림 때문에 합계가 달라 보이면 안내. 분모·비중은 반올림 전 금액 기준
	비중
	표시 소수 자릿수는 일관되게 적용. 합계 반올림 오차를 실제 자금 증감으로 처리하지 않음. 분모 0이면 비중 null·차트 대신 빈 상태
	기준과 시점
	기준일·개인/가구·평가통화·현재/계획·예측 여부를 표시. 가격시각·조회시각·공시일·실적기간은 상세 근거에서 구분
	평가 변화
	이전 동일 범위·동일 정의의 기준값이 있을 때만 증감 표시. 비교 자료가 없으면 전일/전월 수익률을 만들지 않음
	음수
	순자산·현금흐름 적자는 그대로 표시. 자산 도넛 조각에 음수 사용 금지. 부채는 별도 숫자·표
	설명 순서
	확인된 결과 → 계산 이유 → 적용 가정·제약 → 필요한 다음 행동. 수치는 검증된 fact_id와 연결
	차트 접근성
	색상만으로 구분하지 않고 이름·금액·비중을 제공. 차트와 같은 내용을 표로 확인 가능
	

고객에게는 현재 현황·수익 0% 적립 기준·가정 시나리오·자료 미확인 등의 표현을 사용한다. 예측 곡선을 표시하면 실제 관측 구간과 미래 가정 구간을 구분하고 불확실한 결과를 확정 수익이나 성공확률로 이름 붙이지 않는다. 확률모형 미지원 상태는 유지한다.

누락·미지원·정책 미정·수집 실패는 0원이나 후보 없음으로 바꾸지 않는다. 계산 완전성, 제안 가능 여부, 자료 최신성, 세금·비용 반영 상태를 독립 표시한다. 다른 결과의 누락 때문에 A~D 전체를 차단하지 않는다. 일부 결과의 보류를 피하려고 서비스가 임의 수익률·세율·투자비중을 채우지 않는다.

33. 가상 고객의 출력 예시
제25.1절 및 화면 명세의 검산 픽스처를 재사용한다. fixture_only=true인 예시이며, 보호금 6개월은 운영 기본값이나 실제 고객 추천이 아니다. 나머지 자산은 확인된 0원이고 입력 범위가 완전하다는 가정이다. 앱 실행 검증 결과가 아닌 기대 표시다.
영역
	고객이 볼 결과 예시
	공통
	‘가상 예시 · 개인 기준 · 2026-11-02’
	A 자산
	총자산 2,000만원 / 총부채 1,000만원 / 순자산 1,000만원
	A 구성
	현금성 2,000만원·100%. 부채는 도넛 아래 별도 표시
	B 금융자산
	현재 금융자산 2,000만원 / 현금성 100%. 아직 실행하지 않은 투자 제안은 반영하지 않음
	C 목표
	12개월 뒤 필요한 목표금 600만원 / 현재 확보 600만원 / 부족 0원 / 현재 충당률 100%
	C 적립 기준
	이미 목표금이 확보되어 해당 목표의 추가 월 필요 적립액은 0원. 해당 금액을 다른 목적에 중복 배정하지 않음
	D 공통 현황
	세후 월소득 300만원 − 생활비 180만원 − 의무상환 30만원 = 월 잉여현금 90만원
	D 가상 목적배정
	보호금 900만원 + 목표금 600만원 + 장기투자 배정 후보 500만원 = 2,000만원
	D 월 배분
	월 잉여현금 90만원은 확인. 전략별 월 배분 정책이 없으므로 목적별 월 배분은 ‘— · 배분 기준 확인 필요’
	D 투자 구성
	후보 500만원은 표시 가능하되 최종 비중·상품 구성은 ‘검토 대기’. 운영 추천 승인으로 표시하지 않음
	D 세 계획
	세 전략의 정책이 없으므로 서로 다른 금액·도달일을 만들어 채우지 않음
	

신규 투자 후보 500만원은 현금 목적배정의 일부이며 총자산 2,000만원에 다시 더하지 않는다. 부채잔액 1,000만원도 현금에서 즉시 전액 상환하는 계획으로 확인된 것이 아니므로 다시 일괄 차감하지 않는다. 지급일별 의무상환 경로는 별도 검증한다.
34. 다음 단계: 출력 → 계산 → 입력 → 질문 매핑
먼저 위 출력 항목을 기준으로 계산·판정 기준과 필수 입력을 연결한다. 이후 기존 질문을 재사용하고 실제로 부족한 질문만 추가한다. 본 보완은 새 질문 문구·Q-ID·12~20개 또는 약 30개 구성을 확정하지 않는다.

35. 출력 형식 검토·수용 기준
아래 항목은 구현 시 확인할 수용 기준이며 앱 테스트 통과 기록이 아니다.
* A의 자산 합계와 자산 종류별 합계가 일치하며 B·보유내역·연금계좌를 중복 더하지 않는다.
* A·B·P 차트의 분모와 현재/제안 기준이 표시된다. 자산 총액·월 흐름·투자 부분집합을 혼합하지 않는다.
* 부채·적자·순자산 음수와 원형 차트의 비중을 별도로 처리한다. 분모가 0이면 비중을 만들지 않는다.
* C는 현재 확보액과 목표일 예상 재원을 구분하며 목표 충당률을 성공확률로 표시하지 않는다.
* D는 같은 입력·가정·기준일의 세 계획을 비교하며 P1~P5와 혼동하지 않는다. 동일안·불가능안·정책 미정을 정직하게 표시한다.
* 기존 월 납입·의무상환·목표·예정지출·비상금이 원장에서 중복 차감되지 않는다.
* 신규 투자금 0원, 미입력, 미지원, 미확정 정책, 오래된 자료가 서로 다른 표시로 나온다.
* 세전·세후·비용 일부 반영을 구분하고 자료가 없는 세금·수익률·비중을 생성하지 않는다.
* 산업 전망·고객 적합성·비교 후보·최종 편입을 분리하고 제외·사용기간·자료 제약을 유지한다.
* 미리보기는 현재 보유현황과 채택 계획을 변경하지 않는다. 명시적 채택과 실제 실행 기록을 별도 처리한다.
* 모든 표시 숫자는 계산 결과·근거·버전으로 추적되고 설명과 표·차트가 같은 값을 사용한다.
