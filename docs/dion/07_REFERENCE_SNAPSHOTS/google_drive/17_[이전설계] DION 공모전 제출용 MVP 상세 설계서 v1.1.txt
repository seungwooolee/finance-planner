CALC-02/03 현금흐름: 월 잉여현금 = 월 세후 수입 − 정규화된 생활비 − 실제 월 원리금 상환액 − 생활비에 포함되지 않은 기타 의무지출. Q-120은 원금·이자 분리 입력 또는 합계만 입력을 허용. 생활비에 전액 포함되었다면 한 번만 차감하고, 일부 포함/불확실이면 결과 보류.
CALC-04 순자산: 같은 기준일·범위의 자산 합계 − 부채 합계. 전세보증금 미확인이면 확인 자산·부채 소계만 표시하며 '확정 순자산'은 보류. 보증금 반환 전 사용가능현금에 합산 금지.
CALC-07/08/09 보호 및 신규 투자재원: 생존지출 = 필수생활비 + 의무상환 + 별도 의무지출. 비상금 기준은 담당자의 승인된 확보 개월 수만 사용. 투자 가능 신규 현금 = max(0, 실제 접근 가능 현금 − 중복 없는 보호/목표/의무 배정). 월 추가 투자 가능액 = max(0, 월 잉여현금 − 월 보호/목표/의무 적립액). 목적별 배정 합계가 실제 자산/월 여유금보다 클 수 없음.
CALC-10~13 목표: 목표금액(오늘 가치/목표일 명목금액 구분), 월 적립액, 목표 기간, 사용 가능한 목적 자금을 기준으로 부족액과 목표 충당률 계산. 목표 충당률은 성공 확률이 아니다. 투자수익률 또는 물가는 승인된 가정을 별도 표시할 때에만 적용한다.
대출 Q-144 삭제에 따른 제한: 총 부채잔액과 현재 실납부 원리금으로 '현재 월 여력'만 계산. 건별 금리·만기·상환방식 없으면 미래 잔액/정밀 원리금 상환표를 확정하지 않는다.
필수 상태: READY(해당 출력 계산 가능), NEEDS_INPUT(필요 입력 부족), REVIEW_REQUIRED(배분 기준·검증 미승인), INFEASIBLE(재원·시점 위반), NOT_SUPPORTED(현 MVP 외), STALE(입력 변경으로 이전 계산 무효), ERROR(실패). 부분 계산 가능할 때는 다른 카드까지 전부 차단하지 않는다.
7. 계획 3안과 포트폴리오
공통 제약: 같은 고객 입력, 버전, 기준일, 보유 재원, 의무 상환·생활비, 고객이 허용한 조정 범위를 공유한다. 보유자금 배분(current_allocations)과 매월 잉여금 배분(monthly_allocations)을 반드시 나누어 제시한다.
현행 POL-FIN-1.2: 안정안은 유지납입 후 보호 부족을 빠르게 보충한 뒤 목표를 배정한다. 생활비 유지안은 같은 생활비·월 여유금에서 최소 보호 보충과 가능한 목표 추가적립을 병행한다. 목표우선안은 허용 한도 내 필요한 감축만 사용한다. BASELINE 실제 납입 현황은 별도 보존하고 매 회차 부족액·잔여 납입 횟수로 갱신한다.
각 카드에 제시할 값: 현재 보호자금/목표자금, 월 적립액, 남는 월 여유금, 예상 목표 도달일 또는 부족액, 변경한 가정, 장단점, 위험·유동성 제약, READY/NEEDS_INPUT/INFEASIBLE 상태.
현재 자산 현황, 배정 대상 자산의 목적 구성, 월 신규 배분, 투자금 내부 구성을 분리한다. 집·회수 전 보증금을 모두 즉시 배정 가능한 현금으로 보지 않는다. PREF-0.2의 P1~P5는 자기보고 선호(score=null)이며 금융 적합성 진단과 다르다. 기간정책·상품·자금 제약이 미검증이면 투자 비중은 보류한다.
대표 상품 표시: 투자 구성의 역할과 실제 상품명·종류·선택 이유·주요 위험·비용·유동성·기준일·공식 출처를 연결한다. 일반적인 자산군 예시와 고객 조건에 맞춰 선별한 개인화 제안을 구분한다. 검증된 정보·적합성 규칙이 없으면 해당 상품 제안을 보류하고 필요한 정보/검토 사유를 표시한다. 명칭만 ‘대표 상품’으로 바꿔 검증을 생략하지 않는다.
8. AI 에이전트 설계 및 비용
기본 간편진단은 AI 호출 0회: 서버 규칙으로 필수 질문 선택, 데이터 검증, Python Decimal 계산, 상태 판정, 기본 템플릿 설명. AI는 사용자가 '이유 설명' 또는 복잡한 상황 질문을 선택했을 때만 호출한다.
AI가 할 일: (1) 검증된 Q-ID에서 필요한 다음 질문을 선택·자연어로 설명, (2) Python 도구의 fact_id/fact_refs를 인용해 결과 해설, (3) 고객이 허용한 변경 범위를 입력받아 서버에 재계산 요청, (4) 답변의 가정·불확실성을 설명.
AI가 하면 안 되는 일: 고객이 입력하지 않은 금액 확정, 원/년·월 단위 혼용, 임의 세율·이자·상품 공시 발명, 승인 전 목표/계획 채택, 필수자금 투자 유도, 실거래 실행, 자기 판단으로 규칙·코드 임의 변경.
호출 흐름: POST /analyze → server 검증된 analysis_run/facts 수집 → LLM 구조화 출력 → 실제 fact_id와 숫자·출처 일치 검증 → 부적합 결과는 문구 폐기 후 계산 엔진 템플릿으로 대체. 로그에 model, prompt_version, run_id, 요청/응답 토큰, 검증 결과·오류코드 기록. LangChain/LangGraph는 필요성 검증 후 추가하고 단일 제어기 우선.
9. 기술 스택·DB·API
프론트: Next.js + TypeScript + Tailwind CSS + shadcn/ui + Recharts. 백엔드: FastAPI + Pydantic + Decimal + pytest. DB: 초기 가상 고객 단일 데모는 SQLite로 빠르게 개발할 수 있으나 배포·동시 사용·이력관리를 고려하면 PostgreSQL 권장. GitHub 버전 관리, 프론트 Vercel/백엔드 Render 등 현재 기술 설계에 맞춘 배포. 실제 계정/연동 기능은 제외.
최소 DB 엔터티: cases(가상고객·범위), profile_versions(변경 전후), field_values(값/상태/단위/출처), analysis_runs(시점·모드·가드·상태), calc_facts(확정 숫자/근거), plan_candidates(3안), plan_adoptions(고객 명시 채택/버전), allocations(현재 자산/월 흐름 분리), monthly_actions(행동·기한·실적), reviews(원안 vs 실제 vs 수정안), ai_audit(요약·검증·비용). 개인식별정보 불필요 수집 금지.
API 구현 계약(기존 경로 우선): GET /health; POST /interview; POST /diagnose; POST /portfolio/allocate; POST /plans 또는 기존 /redesign(3안 생성); POST /plans/adopt; POST /plans/{id}/actions; PATCH /actions/{id}; POST /monitor/review; POST /analyze(선택). 구체적 경로는 현재 저장소 확인 후 최종 확정하고 중복 생성하지 않는다.
필수 응답 메타: case_id, profile_version, run_id, rule_version, assumptions, status, issues, data_as_of, facts[], missing_fields[], applied_guard_ids[]. 프론트 카드와 AI 해설은 같은 run_id의 facts를 사용. 입력 변경 시 이전 run은 STALE로 전환.
10. 테스트·검증 및 데모
원장에는 시트 PASS 기록 55건이 있으나 앱 테스트 89건은 미실행. 새 MVP는 이력을 참고하되 실제 UI/API/계산 테스트를 별도 실행·증빙한다.
필수 자동 테스트: T1 월300만−생활220만−원리금20만=여유60만; T2 부채0이면 여유80만; T3 생활비에 원리금 포함 시 이중 차감 금지; T4 전세보증금 미확인 시 순자산 미확정; T5 목표자금·비상금·투자자금 중복 배정 금지; T6 목표를 맞추려 미승인 수익률 자동 삽입 금지; T7 부채 건별 정보 부재 시 상환표 보류; T8 계획 선택 미리보기와 채택 상태 분리; T9 실행 DONE만으로 목표 달성 처리 금지; T10 가상 1개월 후 차이를 반영한 수정안 고객 채택 이전까지 기존안 유지.
AI 비판적 검증: 비어 있는 보증금을 0원으로 설명하도록 유도하는 테스트; 투자 위험선호만 보고 고위험 배분을 단정하도록 유도하는 테스트; 미등록 상품 금리·수수료 질문; fact_refs에 없는 숫자 생성 테스트. 오류를 포착·차단하고 재실행 로그를 남겨 공모전 AI 활용 기술서에 정리.
필수 E2E 데모: 대표 고객 입력 → 진단 → 보호자금과 투자 가능액 → 세 계획 비교 → '이 계획으로 시작하기' → 행동 2~3개 기록 → 가상 한 달 후 실제 지출·저축 입력 → 이전과 다른 수치 재계산 → 수정 계획 채택 → 원본/수정 기록 둘 다 확인. 투자 가능·투자 보류·정보 부족 세 사례도 확인.
