구현 상태: GitHub 현재 구현은 frontend/ Next.js+React+Tailwind+Recharts, backend/app/main.py FastAPI, models.py Pydantic, engine.py Decimal, GET /health, GET /api/sample-profile, POST /api/calculate 및 pytest/Playwright이다. PostgreSQL, 인증/세션, 3안 플래너, LangChain/Graph/Smith, 배포·관측은 제안된 확장이며 현재 코드에 구현됐다는 뜻이 아니다.
2. 백엔드 내부 세부 설계
flowchart TB
   R[FastAPI Router]
   A[권한 · 요청 추적 · Rate Limit]
   V[Pydantic v2 계약 검증]
   D[Domain Service / Transaction Manager]
   R --> A --> V --> D
   D --> Q[InterviewService\n질문 스키마 · 조건부 질문 · 정보 누락]
   D --> FIN[DiagnosisService\n월 잉여금 · 순자산 · 자금 접근성]
   D --> PO[PortfolioService\n사용 목적 배분 · 투자 가능 자금]
   D --> PL[PlanService\n3안 비교 · 명시적 채택]
   D --> EXEC[ActionReviewService\n실행 기록 · 가상 한 달 후 재점검]
   D --> AG[AgentService\nLangGraph 선택 호출]
   Q --> DB[(PostgreSQL)]
   FIN --> C[Pure Python Decimal Engine]
   PO --> C
   PL --> C
   EXEC --> DB
   PL --> DB
   AG --> TOOLS[승인 도구: get_missing_questions, calculate_diagnosis, compare_plans, explain_facts]
   TOOLS --> C
   AG --> CHECK[답변 fact_id/run_id 교차 검증]
   CHECK --> DB
책임 분리: API 라우터는 HTTP, 서비스 계층은 업무 흐름, 재무 엔진은 계산, 저장 계층은 변경 이력을 담당한다. 금융 계산은 OpenAI API나 LangChain 코드에 의존하지 않게 유지한다. Decimal 금액을 원 단위 문자열로 직렬화하고 원/월/연·개인/가구 기준을 검사한다.

3. AI 에이전트 흐름
flowchart TD
    START[사용자 '왜 이런 결과인가요?' / 추가 설명 요청]
    LOAD[DB에서 case_id, profile_version, run_id 조회]
    MISSING{필요한 입력이 빠졌나?}
    QUESTION[검증된 질문 원장의 Q-ID만 반환]
    TOOL[FastAPI 승인된 계산 도구 호출]
    FACT[계산 엔진: 수치·가정·fact_id 반환]
    EXPLAIN[LangChain LLM: 자연어 해설 초안]
    CHECK{숫자·근거·제약 일치?}
    OK[검증된 설명 UI 출력]
    FALLBACK[정적 설명 템플릿 반환 + 로그]
    START --> LOAD --> MISSING
    MISSING -- 예 --> QUESTION
    MISSING -- 아니요 --> TOOL --> FACT --> EXPLAIN --> CHECK
    CHECK -- 통과 --> OK
    CHECK -- 실패 --> FALLBACK
* LangChain: 모델 호출, Tool Calling, 구조화된 JSON 출력, 프롬프트 버전.
* LangGraph: 노드 전이, 대화/요청 상태, 재시도, 조건 분기, 체크포인트. 장기적 멀티 에이전트는 MVP 제외.
* LangSmith: AI 응답 추적, hallucination 검증 케이스, 비용·지연 평가. 개인정보/재무 실입력값 자동 업로드 방지.
* AI 없는 경로: 간편 진단·금액 계산은 LLM 호출 0회로 동작 가능해야 함.
* 사용자 계획 채택, 자금이체, 실제 금융상품 권유는 LLM이 자동 확정할 수 없음.

6. 외부 데이터와 RAG
* Google Sheets: 사람·재무 담당자가 편집하는 승인 전 설계 원장. 운영 요청 시 실시간으로 시트 내용을 무검증 반영하지 말고, 검증·버전 고정·서버 적재 단계를 거친다.
* 실제 상품: 공식 공시, 기준일, 자격, 위험등급, 비용, 유동성, 출처 URL을 검증한 상품만 비교 대상으로 사용한다. 현재 검증 상품 0건이므로 MVP는 상품군 교육 중심.
* RAG/pgvector: 공식 문서 수가 적으면 단순 SQL·JSON 근거조회로 충분하다. 문서가 커지고 검색 품질 평가가 확보될 때 pgvector 등 검색 계층 도입.
* LLM Provider: 어댑터 뒤에 두어 바꿀 수 있도록 한다. 유료 API는 최소한의 설명 요청에서만 사용한다.
7. DEV / QA / CI-CD 구조

    A[Google Drive 원장·재무 검증] --> B[VS Code + Codex + ECC]

* Codex/ECC: 코드를 작성하는 개발 도구, 고객 웹 앱에서 작동하는 금융 AI가 아니다.
* ECC: 계획→테스트→구현→코드리뷰→검증 루프와 보안·리팩터링 룰을 Codex에 붙이는 선택 도구. 공식 github.com/affaan-m/ECC을 확인하고 하나의 설치 경로만 선택한다.
* 테스트: Ruff, pytest, pip check, TypeScript, ESLint, Playwright, 빌드. GitHub Actions에서는 임의의 금융 공식 변경이 golden test를 깨는지 확인.
* 배포: Vercel과 Render 등은 후보이며 실제 요금·스케일·보안 적합성 검토 후 결정. 프로덕션 DB는 관리형 Postgres 선택 가능.
* 모니터링: OpenTelemetry/구조화 로그/AI 검증 trace. 원본 개인정보는 tracing에 직접 전송 금지.
8. 단계별 도입 순서
1. 기존 GitHub 코드·회귀 테스트 보존; 60개 질문 중 대표 데모 P0 질문과 OpenAPI v1 계약 우선 확정.
2. FastAPI services/ 도메인 구조 + 계산 엔진의 상태 판정 강화(보증금, 대출, missing fields).
3. PostgreSQL·Alembic으로 profile/version, run_id, plans, 실행·리뷰 이력.
4. Next.js 카드형 UX와 진단·3안 비교 화면; 프론트 숫자 재계산 금지.
5. 3안 계획 비교와 고객 채택/행동/한 달 후 점검 수직 슬라이스 완성.
6. LangChain을 활용한 하나의 선택형 AI 해설 기능 추가; 수치·근거 대조 후 LangSmith 평가.
7. 필요성이 증명되면 LangGraph 다단계 상태 전이·체크포인트 도입(처음부터 멀티 에이전트 불필요).
8. GitHub Actions·배포·보안·접근성/모바일·E2E 데모 및 공모전 보고서 근거 확보.
9. 핵심 미확정 사항
비상자금 보호 개월 수, 계획 3안별 허용 조정 범위, 투자 자산군/배분 비중, 기존 장기투자금 200만원의 목적 배정, 특정 금융상품 제공 범위와 공식 자료 검증, 실서비스 인증·개인정보 처리 정책. 미승인 항목은 오류가 아니라 REVIEW_REQUIRED / NEEDS_INPUT 상태로 표시한다.
