빠른 진단은 확인된 현재 상태, 우선 확인·실행할 과제 1~3개, 투자계획을 위해 추가로 확인할 정보를 제공한다. 상세 입력이 부족한 합계·차액은 확인된 범위를 표시하고 투자 가능액·완성된 포트폴리오로 확정하지 않는다. 정밀 진단은 빠른 진단의 응답을 이어받아 고객이 요청한 결과에 필요한 부족한 정보만 보완하고, 정책·상품 검증이 확인된 범위에서 목표 준비·두 재무계획·투자 구성·실행·점검으로 연결한다. 두 모드는 별개 설문이 아니라 같은 고객정보를 이어 사용하는 진단 깊이의 구분이다. 이번 승인으로 질문 수·새 ID·미검증 배분 정책까지 확정하지 않는다.
재구성은 전체 보유자산과 부채·목표·가용시점·변경 제약을 파악한 뒤, 보호·목표자금과 의무지출을 제외한 신규 일시금·향후 납입금으로 먼저 조정한다. 이것만으로 목표 구성을 충족하지 못하는 경우에만 필요한 범위의 기존 금융자산 변경을 제안한다. 불필요한 전체 매각·교체를 기본 경로로 삼지 않는다. 재구성 방향은 확정하되 목표 비중·허용 편차·매매 비용·세금의 수치 규칙은 후속 검증 대상이다.
부동산은 최대한 유지한다. 보유 규모·부채·유동성은 전체 재무현황과 제약에 반영하되 기본안에 매각·추가 담보차입을 넣거나 미확정 매각대금·보증금 회수액을 투자 재원으로 사용하지 않는다. 금융자산 목표 구성의 비중은 명시한 분석 대상 금융자산 범위에서 계산하며, 부동산 평가액에 주식·채권 비중을 곱해 매수 필요액을 만들지 않는다. 부동산 변경이 있어야만 가능한 목표는 현재 조건의 부족을 설명하고 고객이 허용한 다른 조정부터 검토한다. 보험·연금 제외 범위는 유지한다. 매도·교체의 긴 설명은 AI 상담·상세보기에 두고 필요한 실행 조건은 해당 시점에 확인한다.

v3.3 · 6단계별 완료 계약
PROC-01 관계 정립: 서비스 범위·한계·AI 역할·고객/플랫폼의 책임·정보 이용을 안내하고 필요한 확인·동의를 기록한다. 전문자격 보유를 허위 표시하지 않는다.
PROC-02 정보·목표: 고객 확인 재무정보·최우선 목표1개·목표 이유·생활 유지 조건·조정 허용 범위·미확인 값을 저장한다. 민감한 원문·증빙을 필수 입력으로 추가하지 않는다.
PROC-03 분석: 현금흐름·자산/부채·유동성·목표 부족액과 강점·걸림돌을 근거에 연결한다. 출력별 필수값 부족 시 해당 결과만 보류한다.
PROC-04 제안: 동일 기준의 세 안 비교·수정 요청·채택/보류를 저장한다. 미리보기와 실제 채택을 구분한다.
PROC-05 실행: 채택 계획에 연결된 월 행동·상태·실제 실행 기록을 저장한다. 미리보기 변경으로 실행계획을 바꾸지 않는다.
PROC-06 모니터링: 점검 범위·방법·주기·다음 날짜를 고객과 확인하고 실적·변화·차이·회귀 단계·수정안 채택을 보존한다. 수동 점검은 P0, 자동 알림·외부 수집은 후속이다.
단계 상태는 계산 domain_status(READY 등)와 분리한다. process_stage=1..6, stage_status=NOT_STARTED|IN_PROGRESS|NEEDS_CONFIRMATION|COMPLETE|REOPENED. 목표 미정이면 ②에 남으면서 가능한 현재 진단은 제공한다. ⑥ 완료 후 다음 점검을 기록한다.

필드·조건식 정리 과제
* risk_preference / investment_risk_preference, loss_response / investment_loss_reaction, invest_horizon / investment_horizon, invest_experience / investment_experience는 중복 후보다. 의미·선택지를 비교한 뒤 대표 필드와 별칭 매핑을 승인한다. 경험 기간 investment_period와 미래 사용 기간은 합치지 않는다.

상품군·개별 상품 지원 수준
07_상품군검증15는 15개 유형의 범위/표시 단계다. ‘핵심’은 개발 범주이고 고객 적합성 통과를 뜻하지 않는다. 실제 상품명·공시·기준일·위험·비용을 검증한 개별 상품은 현재 0건이다.
기본 출력은 상품군 교육과 제외 이유다. 개별 상품 후보는 데이터 검증·재무 검토가 완료된 경우만 노출한다. STRUCTURED는 MVP 자동 추천 제외, DEBT_PLAN은 행동계획으로 분리한다. 법적 검토 후보 링크는 검토 완료 증거가 아니다.
API 응답에 question_registry_version, rule_approval_version, support_level(CLASS_EDUCATION/VERIFIED_PRODUCT_COMPARISON), issue_code, applied_guard_ids를 연결한다. 입력 부족과 미승인 규칙·상품 근거 부재를 서로 다른 사유로 반환한다.
LangChain·LangGraph 서버 계층
FastAPI 내부에 LangChainAdapter와 LangGraph 실행 계층을 단계적으로 추가한다. AI 모델 연결·구조화 출력은 LangChain, 질문·시나리오 상태 분기는 LangGraph가 담당한다. 입력·Decimal 계산·승인 조건·상품 근거 검사는 기존 서버 모듈을 직접 호출한다. API 경로와 화면 계약은 유지하며 graph_version을 실행 로그에 추가한다. 상세 계약은 ⑨, 호출 상한은 ⑧ J절을 따른다.
ECC 개발 환경과 품질 관리
AI 코딩 환경에 ECC의 개발 규칙·검증 절차·작업 인계를 선별 적용한다. Next.js/FastAPI·LangChain·LangGraph와 역할을 구분하고 고객 분석 런타임에 필수 의존성을 추가하지 않는다. 실제 Codex 버전별 호환성·설치 범위·기존 설정 병합·검사 명령은 ⑩ 기준으로 확인한다. 현재 설치·구현 여부는 미확인이다.


v3.3 · 채택·실행·점검 API 계약
기존 API를 유지하고 필요한 경로를 구현한다. 추가안: POST /plans/adopt(채택), POST /plans/{plan_id}/actions(월 행동 생성/갱신), PATCH /actions/{action_id}(실행 기록). 기존 POST /monitor/review는 실적·변경 정보·원안 비교와 재설계를 담당한다. 실제 경로명은 기존 코드와 중복 없이 맞춘다.
변경 요청은 세션/case 소유권·plan_version·profile_version·idempotency_key를 검사한다. 명시 선택한 실행 가능 후보만 ADOPTED로 저장하고 해당 기간 기존 활성 계획은 SUPERSEDED로 보존한다. 입력/규칙 변경으로 오래된 안은 재검증 전 채택하지 않는다.
점검은 기존 계획·실행 기록을 보존하고 수정안을 PROPOSED로 반환한다. 고객 채택 후 새 계획으로 전환한다. DONE 기록만으로 목표 달성·전체 단계 완료로 간주하지 않는다. 과거 run/plan/action을 덮어쓰지 않는다.
S04 카드·차트·항목 설명은 같은 candidate/run을 참조한다. S06은 ADOPTED 계획의 행동, S07은 원안·실적·수정안·다음 점검일을 표시한다. 세 안 미리보기는 활성 계획을 바꾸지 않는다.

초기 구현은 단일 실행 흐름과 서버 제어기로 구성한다. 서버는 LangGraph로 질문·계산·제약·출처·종료 조건을 제어하고 LangChain으로 선택형 자연어 해석·설명을 연결한다. 기본 계산 경로는 모델 판단을 거치지 않는다. 자유로운 다중 에이전트·자율 도구 반복은 후속 필요성 검토 대상으로 둔다.
1. 세션에서 최신 고객 상태를 불러온다. 2. 서버가 필수 질문·계산·검증 단계를 LangGraph로 직접 실행한다. 3. AI가 필요한 설명/추출 단계에만 LangChain을 호출한다. 4. 도구 요청이 있다면 허용목록·인자·권한을 검사한다. 5. 결과와 fact_refs를 검증한다. 6. 질문 대기/검증 결과/오류로 종료하며 ⑧ J절의 전체 호출 한도를 강제한다.
고객 답을 기다릴 때는 프로세스를 계속 실행하지 않는다. WAITING_USER 상태와 질문을 저장하고 다음 요청에서 이어간다. 소득·지출 등 고객 값은 서버 상태를 사용하며 AI가 새 프로필을 임의 생성해 계산하지 못하게 한다.
도구 계약 예시
입력: simulate_scenario(profile_version=3, scenario_id='income_gap'). 서버가 case 접근 권한과 데이터 버전을 검증한다. 필수 조건이 부족하면 status=NEEDS_INPUT, missing_fields, 질문 이유를 반환하고 금액 결과를 만들지 않는다.
계산 성공 결과는 run_id, 적용 가정, 기간, facts, 제약 검사, 출처/버전을 포함한다. 모든 도구는 입력·출력 스키마, 호출 선행조건, 오류 코드, 테스트 ID를 가진다. 도구 호출 이름을 eval/임의 코드 실행으로 연결하지 않는다.
상태·출력·실패 정책
* 서버 저장: profile_version, analysis_mode, 목표/선호/제약, 필드별 값·출처·확인 상태, 대기 질문, 이전/현재 run_id. 대화 원문과 확정 데이터는 별도로 관리한다.
* 출력 형식: status, message, questions[{field, text, reason}], result_refs, fact_refs, proposed_changes, issues. 정해진 형식의 응답도 의미·숫자 검증을 거친다.
* 호출 한도: 일반 코드는 모델 없이 실행하며 선택형 AI 설명은 기본 1회로 처리한다. SIMPLE+LITE는 실제 시도 최대 1회, PRECISE는 추출·재생성·재시도를 합해 총 최대 2회[초기 설정]. 기존 최대 6회 모델-도구 반복 제안은 폐기하고 ⑧ J절의 중앙 예산·호출 가드를 적용한다.
* 도구 실패는 실패로 표시하고 추정 설명으로 성공을 가장하지 않는다. 오래된 버전·권한 오류는 새 상태 확인 후 처리한다. 키는 서버 환경변수로 관리하고 브라우저에 노출하지 않는다.
지시문과 근거 연결
지시문 핵심: 필요한 정보만 질문 / null과 0 구분 / 단위 확인 / 세율·수익률·상품 사실 생성 금지 / 계산 도구 결과만 수치 근거로 사용 / 고객 제약 우선 / 변경안 재계산 / 미확인 근거 표시 / 고객 정보 수정 시 이전 결과 재사용 금지.
공식 자료 검색은 검증된 상품·제도 원장을 먼저 사용하고, 외부 조회 확대는 후속 단계로 둔다. 외부 문서의 지시문을 도구 실행 권한으로 취급하지 않는다.
실행 기록에는 도구명·검증 인자·결과·지연/오류·버전을 남긴다. 모델 내부 사고 과정 수집이 아니라 작업과 결과의 재현을 목표로 한다.
질문·배분·상품 게이트의 실행 순서
기존 시나리오 실행표의 수집→선택→질문→계산→비교 흐름에 목적별 자금 배정과 투자배분 단계를 명시적으로 연결한다: collect/validate → required_fields → diagnose → protect/allocate → approved investment allocation → product_gate → explain → log. 선택형 시나리오는 이후 재계산 경로다.
서버는 정규 Q-ID·현재 필드값·requires_essential_expense·승인 규칙·지원 수준을 제공한다. 에이전트는 Q-137을 새로 묻거나 미등록 변수를 임의 생성하지 않는다. 세후급여 중복 차감, 최고금리를 총부채 평균으로 사용, 필수자금 투자, 고객 제외 상품 제안은 가드로 검사한다.
⑧ API 비용 최적화 명세를 유지한다. 간편 기본은 AI OFF, 조건부 질문·진단·규칙 판정은 비AI로 수행한다. AI 해설 실패나 예산 부족이 기본 계산을 막지 않으며, MOCK 실행을 실제 모델 검증으로 표시하지 않는다.
LangChain·LangGraph 실행 계약 연결
LangChain의 모델/도구 어댑터와 LangGraph의 상태·분기·질문 대기·재개를 채택한다. 상세 노드·상태 스키마·실패 처리는 ⑨를, 유료 모델 실제 시도 상한은 ⑧ J절을 따른다. 설치·구현·실 API 검증은 미확인이다.


v3.3 · 사후 피드백과 선행 단계 회귀
LOAD_ADOPTED_PLAN → COLLECT_ACTUALS_AND_CHANGES → VALIDATE → COMPARE → SELECT_RETURN_STAGE → RECALCULATE → EXPLAIN → CUSTOMER_ADOPTION → SAVE_NEW_PLAN. 변화가 없으면 기존 계획 유지와 다음 점검을 기록한다. 고객 채택은 UI의 명시 행동을 서버가 검증한다.
소득·가족·목표·위험 조건 변경은 ②에서 확인한 뒤 ③으로 연결한다. 입력 변화 없는 실적 차이·현금 부족은 ③ 재평가, 배분·목표일 조정은 ④ 재제안, 채택 후 ⑤ 행동 갱신으로 이어진다. 부족한 정보는 관련 결과만 보류하고 필요한 질문을 반환한다.
AI는 근거로 차이·원인을 설명하고 변경안을 제안한다. 목표·소비 절감·위험성향·계획 채택을 임의 확정하지 않는다. 투자 평가손익과 순입출금을 분리하고 저축 차이를 자산 평가액 변화와 동일시하지 않는다. 고객을 비난하거나 미실행을 실패 점수로 단정하지 않는다.

재무설계·공모전 증거
재무설계 사례 60점: 주제·목표 10, 진단·분석 20, 해법·실행 가능성 20, 전달력 10. AI 활용 40점: 활용 능력 20, 비판적 검증 20. 기존 대화의 평가표를 연결한 것으로 제출 전 공식 최신 요강을 대조한다.
‘해법의 실행 가능성’은 고객이 제안된 저축·상환·투자 계획을 현실적으로 실행할 수 있는지에 관한 기준이다. 개발 가능성과 별도로 현금흐름·기간·비상자금·고객 의사를 근거로 보인다.
실제 오류 증거: 최초 출력 → 발견 오류 → 독립 계산/근거 → 코드·규칙·지시문 수정 → 재실행 결과. 개발용 사례와 최종 평가 사례를 분리하고 성공 사례만으로 품질을 판단하지 않는다.
점진적 개발 완료 게이트
G1 관계·범위 확인과 최소 정보·목표 → G2 독립 진단 → G3 공통 제약·세 가지 계획 비교 및 채택 → G4 이번 달 행동 기록 → G5 가상 한 달 후 점검·재설계 및 수정안 채택 → G6 전체 흐름·보고서·AI 근거 검증. 모두 첫 MVP 필수다. 개별상품·거시경제·자동 알림은 핵심 완료의 선행조건으로 두지 않는다.

결정 상태: [제안]. 기본값·모델·횟수·예산은 실제 서비스 측정 및 담당자 승인 후 확정. 구현 상태: [미확인/미실행]. 본 명세는 ①~⑦의 6화면·간편/정밀 질문·두 포트폴리오·상품 검증 구조를 우선하며, 과거 12개 조합은 MVP 필수 대상이 아니다.
A. 최종 권장 방식 — 간편은 API 0회가 기본
권장 결정: 간편 진단의 기본값은 AI 미사용(OFF)으로 설정한다. 재무진단과 제한된 설명은 Python 계산·규칙·검증된 템플릿만으로 제공한다. 사용자가 ‘AI로 쉽게 설명받기’를 선택한 경우에만 저비용 모델 1회 호출을 허용한다. 정밀 진단도 계산은 항상 비AI로 처리하며 AI 심층 해설·재설계는 별도 사용자가 명시 요청한 경우에만 실행한다.
중요한 구분: analysis_mode=간편/정밀은 ‘수집 정보의 깊이’이고 ai_assistance=OFF/LITE/FULL은 ‘AI 사용 수준’이다. 두 값을 동일한 필드로 합치지 않는다. 예: 정밀 입력을 완료했더라도 AI OFF 분석은 가능하고, 간편 입력에서 LITE 설명을 받아도 정밀 투자 적합성 판정이 자동 승인되지 않는다.
A-1. 사용 모드와 호출 정책
• SIMPLE + OFF [기본]: 비용 0원(LLM 호출 0회). 조건부 질문·현금흐름·순자산·목표 부족·누락정보·지원 범위 내 안전 경고를 규칙/템플릿으로 출력. 정밀 투자배분에 필요한 입력이 없으면 확정 추천 보류.
• SIMPLE + LITE [명시적 선택]: 화면의 ‘AI 간단 해설’ 버튼을 누른 경우에만 gpt-6-luna 같은 저비용 모델 최대 1회 호출[잠정]. 허용: 계산 사실의 쉬운 한국어 요약, 누락항목 설명. 금지: 미검증 수익률·상품 추천 생성, 규칙 차단 해제.
• PRECISE + OFF: 정밀 질문/진단·자산 목적별 배분·검증된 투자자산군/상품 후보 조회를 비AI 규칙으로 수행. 입력과 규칙이 불충분하면 보류; 사용자에게 검증된 고정 설명을 제공.
• PRECISE + FULL [명시적 선택]: AI 해설·재설계 요청 시 저비용 모델부터 시도하고 품질/제약 검증 실패 시 상위 모델 재시도 여부를 사용자 정책과 예산 내에서 판단. 자동 상향은 기본 OFF[제안]; 재설계안은 서버 계산으로 재검증.
• DEV_MOCK [개발 전용]: 외부 AI API를 0회 호출하고 고정 JSON fixture로 UI·API·에이전트 흐름 테스트. 화면에 '모의 AI 응답'으로 표시하고 실제 모델 검증 증거로 사용하지 않음.

S07 / POST /monitor/review: 실적·변경 정보와 이전 채택 계획을 비교하고 ②~④ 중 필요한 단계로 돌아가 계산·STALE 판단을 수행한다(0회). 수정안은 고객 채택 전 PROPOSED로 유지한다. AI 설명은 고객 요청 시에만 /analyze를 선택 호출하며 /redesign의 수치 계산은 LLM 없이 수행한다.
서버 호출 판정 순서: ① 비AI 계산/필수값/위험·상품 검증 → ② 결과 캐시 조회 → ③ 사용자 AI 요청·권한 확인 → ④ 예산·호출 횟수 검사 → ⑤ 모델 선택 → ⑥ 응답의 수치·근거·제약 검사 → ⑦ 같은 run_id로 표시. 필수 정보가 없거나 검증 실패 시 AI에 의존해 결과를 꾸며내지 않는다.
C. 모델 라우팅·토큰 절감 정책
모델 ID는 출시·계정 지원·가격이 변경될 수 있으므로 서버 설정에서 관리하고 배포 전에 공식 모델 목록을 확인한다. 개발 기준 후보: 저비용 gpt-6-luna, 품질 보완 gpt-6.1-terra, 복잡한 최종 비교/평가에만 gpt-6.1-sol. 지정 ID는 실제 접근 가능 여부를 테스트한 뒤 사용한다.
라우팅 정책[잠정]: 질문 표현/짧은 사실 해설 → LUNA(낮은 reasoning effort); 고객별 다조건 요약·설명 충돌 수정 → TERRA(정당화된 경우); 어려운 반례 실험·별도 비교평가 → SOL(개발자 승인 시). 1차 응답 성공 시 상위 모델 재호출 금지. 모델 품질은 고정된 검증 사례로 측정하며 싸다는 이유만으로 적합성·안전성을 희생하지 않는다.
토큰 입력 최소화: 전체 고객 대화·계좌별 상세 원장을 무조건 보내지 않는다. 검증된 facts/result_refs, 필요한 제약·질문 필드, source_id, 짧은 프롬프트 버전만 전달. 수치·상품근거·계산규칙은 프롬프트에 장황하게 중복 전송하지 않는다. 출력은 JSON Schema + 필요한 섹션만, max_output_tokens는 LITE 400~600, FULL 800~1200부터 실험[잠정].
프롬프트 캐싱과 앱 응답 캐시를 구분한다. 프롬프트 캐싱은 같은 지시문 접두부의 입력 토큰 비용을 낮추지만 출력 생성은 매번 과금될 수 있다. 길이·TTL·캐시 쓰기 비용 조건을 공식 문서에서 확인한다. 앱 응답 캐시는 완전히 동일한 분석/모델 요청을 재호출 없이 재사용하는 방식이며 0회 호출이 가능하다.
실시간 고객 요청은 일반 동기 호출을 우선. 여러 평가 사례를 사후에 일괄 실행할 때만 Batch/Flex 처리의 가격·지연·실패 가능성을 비교한다. 웹 검색·파일 검색 등 별도 과금 도구는 MVP에서 상시 자동 호출하지 않으며, 먼저 검증된 상품·제도 원장을 이용한다.
D. 애플리케이션 캐시 · 무효화 · 정보 보호
AI 결과 캐시 키 구성[설계 제안]: 사용자/가상 case 범위 + profile_version + run_id + analysis_mode + ai_assistance + facts_hash + assumptions_version + rules_version + calculation_version + product_data_version + prompt_version + model_id + output_schema_version. 캐시 재사용 시 실제 계산 수치·출처·보안 컨텍스트가 동일해야 한다.
키 구현 시 비밀번호·원문 개인정보를 그대로 캐시 키로 사용하지 않는다. 캐시 저장은 사용자/세션별 접근 통제, 암호화·보유기간 정책에 따르며 가상 고객이 기본. 공유 캐시에 실제 고객 재무정보·원문 프롬프트를 무분별하게 저장하지 않는다.
캐시 무효화: 소득·지출·자산·목표·위험도 수정 → 새 profile_version → 기존 결과 STALE; 상품 데이터/공시일/규칙/프롬프트/모델/계산 버전 변경 → 영향받는 해설·결과 재검증. 상품 원장의 검증 기한이 경과한 정보는 캐시된 해설만으로 유지하지 않는다. 캐시 만료일은 데이터 유형에 따라 설정하고 처음에는 보수적으로 운용한다.
재시도/중복 호출 차단: 버튼 연속 클릭에는 idempotency_key와 진행 중 요청 잠금 적용. 네트워크 재시도는 상태와 비용 발생 여부를 확인한 후 제한적으로 실시한다. 사용자가 동일한 run의 설명을 다시 열면 재호출하지 않는다.
E. 비용 상한·계측·실패 정책
개발 기본은 AI_MODE=mock. 실 API 모드는 사용자 의도와 환경 설정이 명시적으로 일치해야 활성화한다. OPENAI_API_KEY는 서버 비밀 환경변수에만 보관하고 Git/프론트/로그에 기록하지 않는다. 최초 검증에서는 가상 고객 사례만 사용한다.
예산 초기안[잠정]: 개발·평가 총 $10, 앱 자체 일일 한도 $1, 간편 LITE 1회/요청, 정밀 FULL 기본 1회/명시 요청 및 검증 필요 시 제한적 추가 호출. 운영·팀·실측량에 따라 수정 가능. 제공자의 결제/프로젝트 예산 경고를 하드 차단으로 오해하지 말고 서버 측 원자적 비용 예약·호출 제한·정산 정책을 둔다.
비용 계산: 모델별 일반 입력/캐시 읽기/캐시 쓰기/출력 토큰 수 × 호출 시점 단가 ÷ 1,000,000 + 과금되는 도구 호출 비용. 추정치와 실제 대시보드 청구액을 별도 기록. usage 메타데이터가 없거나 단가가 미확인되면 비용을 0으로 확정하지 않고 COST_UNVERIFIED로 표시한다. 동시 호출·재시도·실제 청구 지연으로 초과 가능성을 고려해 안전 여유분을 둔다.
필수 로그 필드: request_id, case_id(가명), run_id, profile_version, api_mode, analysis_mode, model_id, prompt_version, schema_version, cache_status, model_calls, tool_calls, input_tokens, cached_input_tokens, cache_write_tokens, output_tokens, estimated_cost_usd, charged_cost_check, latency_ms, validation_status, error_code, created_at. 고객 원문과 API 키는 기록하지 않는다.
예산 소진·모델 실패 시: 기본 수치·비AI 분석은 정상 제공. 선택형 AI 설명은 ‘현재 AI 설명을 제공할 수 없습니다. 계산 결과와 검증된 기본 설명은 확인할 수 있습니다.’로 표시. 더 비싼 모델로 무단 전환하지 않는다. 투자 적합성·상품 공시 미확인은 실패 없이 생성형 문장으로 메우지 않고 NEEDS_INPUT/REVIEW_REQUIRED로 유지한다.
F. API 응답·데이터 계약 추가
POST /analyze, /redesign 공통 요청(추가 필드): case_id, run_id, profile_version, analysis_mode, ai_assistance, user_requested_ai, request_id, expected_output_sections. 서버는 mode·권한·요청된 단계·예산을 검사한다. ai_assistance=OFF이면 모델을 호출하지 않고 template_explanation과 facts를 반환한다.
응답 추가 필드: explanation_source=RULE_TEMPLATE | LLM | MOCK, model_used=null 또는 model_id, ai_calls, cache_hit, estimated_cost_usd, reason_for_skipping_ai, facts_refs, warnings, status, stale_reason. 클라이언트에는 필요 최소 비용 상태만 전달하고 내부 한도/키는 노출하지 않는다. 어떤 모드든 재무 수치는 같은 검증된 run에서만 읽는다.
설정 예[값은 잠정]: AI_MODE=mock ; AI_DEFAULT_ASSISTANCE=off ; AI_MODEL_LITE=gpt-6-luna ; AI_MODEL_FULL=gpt-6.1-terra ; AI_MODEL_EVAL=gpt-6.1-sol ; AI_MAX_LITE_CALLS=1 ; AI_ALLOW_AUTO_UPGRADE=false ; AI_DAILY_BUDGET_USD=1 ; AI_TOTAL_BUDGET_USD=10. 비밀키는 .env.example에 실제 값 없이 변수 이름만 적는다.
G. 인수 테스트와 측정 지표 (신규 T-COST)
T-COST-01 간편+OFF → 고객 입력부터 진단·그래프·경고까지 실제 외부 LLM 호출 0회, 계산 결과 정상.
T-COST-02 간편+LITE에서 ‘AI 설명 요청’ 전에는 0회, 명시 클릭 후 설정상 최대 1회; 서버 가드로 강제.
T-COST-03 정밀+OFF → 투자 가능액·위험 차단·상품 원장 검증은 비AI로 처리하고 미확인 입력은 보류.
T-COST-04 입력/규칙/상품/프롬프트 버전이 동일한 재조회 → 캐시 적중 시 0회. 고객정보/공시가 바뀌면 STALE 처리 후 적절히 무효화.
T-COST-05 API 실패·예산 부족·타임아웃 → 비AI 재무진단 유지, 사용자에게 명확히 안내, 상위 모델 무단 재호출 없음.
T-COST-06 AI가 설명한 금액·비중·상품 사실이 계산 facts/source_id와 다르면 출력 차단/수정, 부적합 추천 금지.
T-COST-07 실제 호출 사용량·캐시 과금·출력 토큰·도구 비용이 누락 없이 기록되고 예산 상한 정책이 동시 요청에서도 작동.
T-COST-08 가상 고객 A/B의 캐시 또는 로그가 서로 섞이지 않음; 프로필 수정 시 구버전 해설 재노출 없음.
T-COST-09 Mock 테스트 결과는 실제 API 성능 검증으로 표기하지 않음. 실제 API로 소수 고정 평가 사례를 별도 실행·비교.
T-COST-10 동일 평가 사례에서 OFF/LITE/FULL의 비용, 지연, 필수 질문 누락, 수치 불일치, 출처 정확성, 고객 이해도를 분리 기록. 모델 선택은 이 결과에 따라 승인.
KPI 제안: 간편 기본 경로 LLM 호출 0회(필수); 캐시 적중률·고객당 평균 비용·95백분위 지연·AI 해설 수치 불일치 0건(목표); API 차단 후 진단 정상 제공 100%(목표). 수치는 측정 전 달성 실적으로 쓰지 않는다.

담당: ChatGPT·Codex는 모드/서버 가드/테스트/로그 구현 초안, 이승우는 예산·자동 상향 정책·배포 승인, 이재훈은 간편 설명 범위·정밀 적합성·재설계 검증. 승인 전 상태는 설계 제안이며 구현 완료 아님.

J. LangChain·LangGraph 연동 호출 상한
기술 채택에 따라 유료 모델 호출의 단위를 명확히 한다. 본 절의 상한은 같은 논리 요청(request_id/idempotency_key)의 실제 모델 시도 총량이다. 고객 답변 재개·중복 네트워크 요청·도구 반복으로 횟수를 초기화하지 않는다. 기존 ⑥의 최대 6회 반복 제안은 본 제한으로 대체한다.
초기 개발 설정: AI_MAX_LITE_CALLS=1, AI_MAX_PRECISE_CALLS_TOTAL=2, AI_MAX_REGENERATION_ATTEMPTS=1, AI_ALLOW_AUTO_UPGRADE=false. AI OFF와 DEV_MOCK은 외부 모델 호출 0회. PRECISE 설명은 기본 1회이며 추가 슬롯 하나를 자유 서술 추출 또는 제한된 재생성에 쓸 수 있다. 상한은 할당량이 아니며 검증 실패·예산 부족이면 더 일찍 종료한다.
중앙 ModelGateway에서 SDK/HTTP 자동 재시도·스키마 재시도·모델 전환을 모두 계측한다. 첫 시도가 과금됐을 수 있는 timeout도 사용량 확인 전 0회로 취급하지 않는다. 예산은 기존 E절의 서버 비용 예약·정산을 공유한다. ⑨ F절 및 T-LG-07은 이 설정을 참조한다.
LangChain·LangGraph 오픈소스 라이브러리 사용료와 모델 API·서버·DB·선택형 LangSmith/관리형 배포 요금을 구분한다. 동일 모델·유사 토큰·동일 호출 수라면 큰 API 비용 증가가 필수적인 것은 아니다. 토큰·도구·저장 비용은 실제 로그로 검증하며 절감률을 미리 보장하지 않는다.
K. ECC 개발 도구 사용량 구분
ECC는 개발 환경에 적용하며 서비스 고객 요청의 호출 예산과 분리한다. AI 리뷰·검색·자동 반복에 사용한 개발 모델 비용 또는 구독 사용량을 dev_session_id/task_id로 기록한다. ⑧ E·J절의 서비스 한도는 그대로 유지한다. ECC 도입만으로 고객 API 호출 증가·개발 비용 절감을 가정하지 않으며 도입·측정 계약은 ⑩을 따른다.


⑨ LangChain·LangGraph 실행 명세
2026.11.01 추가 · 기술 채택 결정 반영 · 구현·실행 검증은 미확인
A. 채택 범위와 기존 명세의 관계
AI 연결에는 LangChain, 질문 대기·시나리오 분기·재계산의 상태 관리에는 LangGraph를 사용한다. 기존 Next.js 화면, FastAPI API, Pydantic 입력 검증, Python Decimal 계산 엔진을 유지하고 서버 내부에 실행 계층을 추가한다. 본 문서 반영은 설치·구현·테스트 완료를 뜻하지 않는다.
기본 실행은 서버가 정한 흐름으로 진행한다. 금액 계산·필수값 검사·규칙 및 상품 근거 검증은 일반 코드가 수행한다. LangChain의 모델 연결은 선택형 자연어 해석·질문 표현·결과 설명에 사용한다. 기술 채택만으로 API 호출을 늘리거나 금융 판단을 모델에 넘기지 않는다.
우선 적용: ② 입력 원장 → ③ 계산 → ④ 승인된 제약·배분 → ⑤ 지원 수준·API → ⑥ AI 동작 → ⑧ 호출·예산 정책을 본 실행 흐름에 연결한다. 미승인 규칙·미등록 변수·미검증 상품은 라이브러리 도입으로 활성화하지 않는다. 본문과 99 보관 탭의 과거 반복 실행안이 충돌하면 현행 ⑧과 본 탭의 제한을 따른다.

입력/API 요청 → load_context → validate_profile → resolve_required_fields → run_domain_calculations → evaluate_approved_constraints → apply_product_gate → select_explanation_path → validate_output → persist_result 순서로 구성한다. 각 노드는 작은 함수로 구현하고 필요한 단계만 실행한다.
load_context: 세션 접근 권한, case_id, 최신 profile_version, 적용 원장·계산 버전을 확인한다. validate_profile / resolve_required_fields: 정규 Q-ID·타입·enum·활성 여부·분석별 필수값을 코드로 검사하고 missing_fields와 질문 이유를 반환한다. 비활성 질문을 모델이 복원하거나 파생값을 고객 입력으로 바꾸지 않는다.
정보 부족: 관련 계산을 보류하고 필요한 질문만 반환한다. 간편 진단에서 계산 가능한 항목은 계속 제공하되, 목표·대출·보증금 등 미확인 값에 의존하는 지표를 확정하지 않는다. 대기 상태를 저장하고 요청을 종료하며 사용자 응답을 기다리는 동안 모델을 반복 호출하지 않는다.
run_domain_calculations: 기존 diagnose_finances / simulate_scenario / allocate_portfolio 모듈을 서버가 직접 호출한다. evaluate_approved_constraints / apply_product_gate: 승인된 조건과 지원 범위를 적용한다. 자금 부족을 높은 수익률 가정으로 보완하지 않고, 특정 상품 근거가 없으면 상품군 교육 범위로 제한한다.
select_explanation_path: ai_assistance=OFF 또는 DEV_MOCK이면 템플릿/fixture를 반환한다. AI 요청이 있고 입력·권한·예산·출처 조건을 충족하면 LangChain으로 검증 facts와 필요한 맥락만 전달한다. validate_output은 구조·수치 참조·규칙 위반·버전 일치를 코드로 검사한다.
시나리오 비교는 먼저 Python에서 각 경로를 계산하고 비교 facts를 모은 뒤 해설을 한 번 생성한다. 시나리오별 모델 호출을 기본값으로 두지 않는다. 새 변경안은 고객 확정 데이터와 분리해 저장하고 확인된 변경만 새 profile_version의 계산에 반영한다.
D. 상태·입출력 계약
GraphState는 Pydantic 등 타입 계약으로 검증한다. 공통 식별자: request_id, idempotency_key, case_id, thread_id, profile_version, run_id, graph_version. 버전 참조: question_registry_version, rule_approval_version, calculation_version, assumptions_version, product_data_version, prompt_version, output_schema_version.
상태 내용: analysis_mode, ai_assistance, 필드별 value/known·unknown·declined·not_applicable, missing_fields, pending_questions, scenario_id와 confirmed_changes, facts/result_refs/fact_refs, applied_guard_ids, issues, execution_status, domain_status, model_calls_used, reserved_cost_usd. 확정 프로필은 서버 저장소가 원본이며 모델 출력으로 덮어쓰지 않는다.
금액은 내부 Decimal 또는 원 단위 정수로 계산하고 API 경계의 직렬화·반올림은 ③ 기준을 따른다. Decimal을 이진 실수로 변환해 재계산하지 않는다. null과 확인된 0은 구분하고 캐시·체크포인트에도 같은 의미를 유지한다.
execution_status는 RUNNING / WAITING_USER / COMPLETED / FAILED 등 실행 상태다. 외부 domain_status는 기존 NEEDS_INPUT / INFEASIBLE / READY / ERROR / STALE 계약을 유지한다. WAITING_USER는 NEEDS_INPUT과 pending_questions로 표현한다. 체크포인트 저장 성공이나 모델 응답 성공만으로 READY를 부여하지 않는다.
AI 응답은 기존 status, message, questions, result_refs, fact_refs, proposed_changes, issues 계약을 사용한다. 최종 숫자·비중은 동일 run_id의 facts를 화면에서 직접 표시한다. 설명이 참조한 fact_id가 없거나 값·버전이 다르면 해당 해설을 공개하지 않고 기본 설명으로 전환한다.
E. 질문 대기·체크포인트·재개
운영에서는 영속 checkpointer와 서버가 발급한 thread_id를 사용한다. InMemorySaver는 재시작하면 상태가 사라지므로 일회성 개발 테스트에만 사용하고 재시작 복구 증거로 삼지 않는다. 저장 방식과 패키지는 실행 환경·버전 호환성 확인 후 확정한다.
interrupt() 등으로 추가 질문과 대기 상태를 저장한 뒤 HTTP 응답을 종료한다. 재개 요청은 인증·case 접근 권한·thread 소유권·profile_version·원장 버전을 다시 검사한다. resume 데이터도 Pydantic으로 검증하고 승인된 필드만 반영한다. 클라이언트가 보낸 thread_id만으로 접근을 허용하지 않는다.
interrupt가 포함된 노드는 재개 시 처음부터 실행될 수 있다. 모델 호출·비용 예약·외부 쓰기는 대기 노드와 분리하고 idempotency_key 및 저장된 작업 결과로 중복을 막는다. 체크포인트가 API 과금의 정확히 한 번 실행을 보장한다고 가정하지 않는다.
프로필·계산·원장 버전이 변경되면 이전 결과는 STALE로 처리한다. 오래된 체크포인트의 facts를 최신 설명에 섞지 않고 영향받는 단계부터 새 run으로 계산한다. 모델 호출 누적량과 예산은 체크포인트 외 서버 원장에서도 보존해 재개·재시도로 초기화되지 않게 한다.
F. 모델 호출과 비용 통제
모델 호출 상한·예산·토큰·재시도 설정의 원본은 ⑧ J절이다. 그래프 노드 수와 모델 호출 수를 구분한다. LangGraph의 recursion_limit는 그래프 단계의 무한 반복 방지용이며 유료 모델 호출 예산을 대체하지 않는다.
기본 목표: SIMPLE+OFF 및 PRECISE+OFF는 외부 모델 0회, SIMPLE+LITE는 실제 시도 최대 1회, PRECISE의 선택형 설명은 기본 1회이며 전체 실제 시도 상한은 2회[초기 설정]. 자유 서술 추출 또는 재생성이 추가 슬롯을 사용한다. 모든 호출·재시도·모델 전환을 합산하며 예산에 따라 2회 미만에서 중단할 수 있다.
호출 전 중앙 ModelGateway가 접근 권한·AI 요청·잔여 호출·예산을 원자적으로 검사하고 비용을 예약한다. SDK 자동 재시도는 중앙 정책으로 통제하고 숨은 추가 시도를 막는다. 모든 유료 모델 경로는 이 Gateway를 통과하며 모델 공급자 키는 서버에만 둔다.
동일 입력·버전의 해설은 ⑧ 캐시 정책으로 재사용한다. 전체 대화·전체 시트 대신 현재 분석에 필요한 facts와 승인된 지침만 전달한다. 호출 종료 후 usage·실제 시도·예약/정산·검증 결과를 기록한다. LangSmith와 관리형 배포는 선택 사항으로 분리하고 기존 ⑧ 예산에 자동 포함된 것으로 보지 않는다.
G. LangChain 도구·구조화 출력
LLMProvider 인터페이스의 MOCK/LIVE를 유지하고 LangChainAdapter를 내부 구현으로 연결한다. 기본 경로는 모델을 직접 한 번 호출하는 구조화 출력 방식으로 구성한다. create_agent 기반 자율 루프는 초기 기본 경로로 켜지 않는다. 공급자 네이티브 구조화 출력 지원은 선택 모델의 실제 응답으로 확인한다.
도구 노출이 필요한 후속 경로만 기존 허용목록을 연결한다. 각 도구에 입력/출력 스키마, 호출 선행조건, timeout, error_code, 계산/원장 버전, 테스트 ID를 둔다. 모델 인자 검증 후 실행하며 eval·임의 코드·미승인 URL 조회·거래 실행을 도구에 연결하지 않는다. 도구를 일반 코드가 실행하면 모델 호출 수는 증가하지 않지만 외부 서비스 자체 비용은 별도로 기록한다.
구조화 JSON의 형식 성공과 금융 내용의 정확성을 별도로 검증한다. 질문은 기존 정규 필드와 연결하고, 미확인 세금·금리·급여·상품 사실을 생성하지 않는다. proposed_changes는 제안으로 표시하고 사용자가 확정하기 전 계산의 기본 입력을 변경하지 않는다.
H. 오류 처리와 기본 결과 유지
입력/권한/구버전 오류는 계산 전에 종료하거나 NEEDS_INPUT·STALE로 반환한다. 모델 timeout·스키마 오류·수치 불일치에서는 해당 AI 해설만 실패로 표시하고 검증된 기본 수치·템플릿은 유지한다. AI 기능 실패와 기본 계산 엔진 실패를 구분한다.
같은 논리 요청의 재생성은 PRECISE의 총 시도 상한과 예산 내에서 최대 1회만 허용한다. 실패했다고 자동 상위 모델로 전환하지 않는다. 응답 유실·timeout은 제공자에서 과금됐을 가능성을 기록하고 처리 상태 확인 없이 전체 그래프를 재실행하지 않는다.
I. 구현 순서와 검증 증거
1단계: 현재 API·화면과 독립 계산을 유지하고 LangChainAdapter, MOCK fixture, 중앙 호출 가드를 연결한다. 2단계: 하나의 고객 경로에서 계산 facts → 선택형 구조화 설명 → 검증을 실행한다. 3단계: LangGraph로 질문 대기·조건 분기·단일 시나리오 재계산을 연결한다. 4단계: 영속 저장·재시작 복구·중복 호출·비용 계측을 검증한 뒤 시나리오를 확장한다.
패키지 후보는 langchain, langgraph, 선택 공급자 통합 패키지, 필요한 checkpointer다. 실제 설치·호환성 검사를 통과한 버전만 의존성 파일에 고정하고 graph_version을 남긴다. 기존 ⑦ 테스트와 신규 T-LG-01~08을 연결한다. MOCK 통과·실 API 통과·독립 재무 검산을 별도 상태로 기록한다.
완료 증거: 입력 fixture, profile/graph/계산 버전, 선택된 노드·도구, 질문 대기/재개, facts 일치, 실제 모델 호출·토큰·비용, 실패·수정 후 재실행 로그. 문서 추가만으로 구현 또는 테스트 통과를 표시하지 않는다.

⑩ ECC 개발 규칙·검증 명세
2026.11.01 추가 · 개발 보조 기능 채택 · 설치·구현·실행 검증은 미확인
A. 목적과 적용 범위
ECC(Everything Claude Code)는 AI 코딩 도구의 규칙·작업 절차·검증·작업 기록을 재사용하기 위한 개발 보조 구성이다. dion에서는 프로젝트 개발 규칙, 변경 후 검증, 세션 인계 기록을 우선 도입한다. 본 문서의 채택 결정은 로컬 Codex에 플러그인을 설치하거나 훅을 활성화한 증거가 아니다.
역할 구분: LangChain은 서비스의 AI 연결, LangGraph는 서비스의 상태·분기·대기·재개, ECC는 개발자가 사용하는 AI 코딩 환경의 작업 품질 관리를 담당한다. ECC를 고객 분석 API의 런타임 필수 의존성으로 추가하지 않는다. ECC 장애나 미설치가 고객의 기본 재무 계산을 중단시키지 않도록 구성한다.
설계·검토 원본은 기존 메인 시트와 본 명세서다. ECC의 일반 지침이나 세션 메모가 승인된 Q-ID·계산식·가드레일·상품 근거를 덮어쓰지 않는다. ECC의 효과는 프로젝트에서 측정하고 속도·품질·비용 절감률을 사전 실적으로 표시하지 않는다.
B. 우선 도입할 세 가지 기능
B-1. 프로젝트 개발 규칙
기존 프로젝트 AGENTS.md와 필요한 Python·TypeScript 개발 지침을 검토해 ECC 관련 규칙을 충돌 없이 병합한다. 원본 설정을 통째로 교체하지 않고 적용 범위·변경 내역·ECC 출처·검토 버전을 기록한다. 실제 파일 경로와 로드 여부는 설치 대상 Codex에서 확인한다.
필수 도메인 규칙: 미입력/null과 확인된 0원 구분; 계산은 승인된 Python Decimal/정수 정책; 보증금·비상자금·목표자금 중복 배정 금지; 생활비와 대출 원리금 이중 차감 방지; 비활성 질문·미승인 규칙·미등록 변수 임의 활성화 금지; 수치·설명은 동일 run_id와 버전 참조; 미검증 상품·세율·수익률 생성 금지.
필수 실행 규칙: AI OFF와 DEV_MOCK의 외부 모델 호출 0회; SIMPLE+LITE 및 PRECISE 호출 상한은 ⑧ J절 참조; API 키는 서버 비밀값으로 관리; 구현·실행·독립 재무 검산을 분리 기록. 지침 파일만으로 강제된다고 가정하지 않고 서버 검증과 자동 테스트로 핵심 조건을 확인한다.
B-2. 변경 후 검증 절차
ECC의 verification-loop를 참고하되 저장소에서 실제 사용하는 빌드·타입 검사·린트·테스트 명령에 맞춰 조정한다. 예제 명령이나 커버리지 목표를 그대로 의무화하지 않는다. frontend/backend 작업 경로와 환경을 확인하고 저장소의 기존 검사 기준을 유지한다.
입력 변경: 노출 조건·필수값·enum·단위·비활성/별칭·미입력 처리를 검사한다. 계산 변경: 승인된 기대값과 독립 검산, 중복 차감·경계값·월별 시점·자금 합계를 검사한다. 에이전트 변경: T-LG·T-COST를 연결해 OFF 0회·실제 시도 상한·facts 일치·STALE·재개를 검사한다. 화면 변경: 해당 기능의 타입·빌드와 필요한 사용자 흐름을 확인한다.
검사 범위는 변경 영향에 맞춘다. 계산·조건·상태에 영향을 주는 수정은 의미 있는 자동 검사를 실행하고, 문구·여백만 바뀐 경우 관련 표시를 확인한다. 검사 실패를 숨기려고 기대값·금융 기준·린트 설정·필수 검사를 완화하지 않는다. 재무 기대값 변경은 승인 근거와 독립 검산을 먼저 기록한다.
검증 보고서는 변경 범위, 실행한 명령, 종료 코드, 기대/실제 결과, 미실행 항목과 사유, 남은 문제를 포함한다. 도구가 PASS 문장을 생성한 것만으로 통과 처리하지 않는다. 최종 diff에서 요청 외 수정·비밀값·불필요한 의존성·테스트 무력화를 확인한다.
B-3. 작업 기록과 세션 인계
개발 세션 종료 또는 작업 인계 시 추적 가능한 작업 기록을 갱신한다. 기록 위치는 기존 docs/ 구조에 맞춰 정하고 Git으로 버전 관리한다. 기록 필드: task_id, 대상 명세/원장 버전, 변경 파일, 구현 범위, 실제 실행 검사와 결과, 실패/수정 내역, 미해결 사항, 다음 작업, commit_id(커밋한 경우만).
새 세션은 기록과 현재 Git 상태·실제 코드·최신 원장을 대조한 뒤 작업을 이어간다. ‘계획됨’, ‘설치됨’, ‘구현됨’, ‘테스트 통과’, ‘재무 검토 완료’를 서로 다른 상태로 유지한다. 기록이 없으면 통과를 추정하지 않고 확인 필요로 표시한다.
재사용할 기술 패턴은 확인된 해결 방법과 적용 범위·반례·출처를 함께 남긴다. 자동 학습·외부 메모리 저장은 초기 기본 기능에 포함하지 않는다. 세율·상품 조건·위험 기준·고객정보를 학습된 지침만으로 확정하지 않으며 실제 고객 재무 원문·API 키를 인계 파일에 저장하지 않는다.
C. 개발 작업의 실행 순서
작은 기능 선택 → 관련 명세·코드 확인 → 적용 규칙과 기대 결과 정리 → 필요한 검사 준비 → 구현 → 실제 실행 및 영향 범위 검증 → diff 검토 → 작업 기록 갱신 순서로 진행한다. 기존 점진적 개발 G1~G6를 유지하고 기능마다 전체 명세서를 새로 작성하지 않는다.
첫 적용 후보는 ‘대출상환액 중복 차감 방지’ 한 기능으로 둔다. ECC 적용 전후에 동일한 입력 fixture·완료 조건을 사용하고 최초 성공까지 걸린 시간, 수정 횟수, 실제 발견 오류, 검사 실행 여부, 모델 사용량을 비교한다. 통제된 비교가 없으면 ECC가 개선 원인이라고 단정하지 않는다.
D. Codex 호환성과 설치 계약
ECC는 Codex용 경로를 제공하지만 Claude Code와 명령·훅·메모리의 동작이 동일하다고 가정하지 않는다. 적용 시점의 공식 지원표, Codex 버전, 운영체제, Node/실행 환경을 확인한다. 본 단계에서는 설치 명령을 실행하거나 기존 전역 설정을 변경하지 않는다.
도입 전 기록: 공식 저장소 URL, 검토한 release/tag 또는 commit SHA, 라이선스, 설치 대상, 활성화할 규칙·기능, 변경할 파일, 기존 설정과의 충돌. 한 도구에는 한 설치 경로만 사용하고 복사 설치·동기화·플러그인을 겹쳐 설치하지 않는다. 작업 지침과 훅의 실제 로드·실행 여부를 최소 예제로 확인한다.
초기 선택은 개발 규칙·검증 절차·작업 인계다. 자동 다중 에이전트, 상시 AI 리뷰, 외부 MCP·검색, 무제한 반복 수정은 활성화하지 않는다. 일반 코드 검사와 필요한 검토를 먼저 사용하고, 추가 기능은 효과·비용·호환성을 확인한 뒤 별도 범위로 채택한다.
훅은 지원 환경에서만 연결하며 동일 검사가 중복 실행되지 않게 한다. 필수 통과 조건은 프로젝트 검사 스크립트와 CI 등 재현 가능한 검사에도 연결한다. ECC 지침 준수 보고와 강제 실행된 검사를 구분한다. 설치 구성 변경은 diff로 남기고 되돌릴 수 있게 한다.
E. 개발 사용량과 서비스 비용 분리
ECC 개발 보조 사용량은 고객 분석 요청의 model_calls·API 예산과 별도 기록한다. 구독형 개발 도구의 사용 한도와 API 종량 과금도 구분한다. ECC에 API 기반 리뷰·검색·여러 에이전트를 연결하면 그 개발 비용이 증가할 수 있으며, 일반 테스트·빌드도 로컬/CI 실행 자원을 사용한다.
측정 항목: dev_session_id, task_id, 도구/모델, 활성 ECC 기능, 실제 시도/리뷰 횟수, 토큰 또는 제공된 사용량, 추정 개발 비용, 검사 시간, 수정 횟수, 결과. 사용량을 확인할 수 없으면 미확인으로 남긴다. 세션당 개발 예산 수치는 팀 예산 검토 후 확정하며 ⑧의 서비스 한도를 임의 전용하지 않는다.
추가 AI 리뷰는 필요한 변경에 한 번 수행하는 것을 초기 운영안으로 삼고, 반복 리뷰는 실패 원인·수정 범위가 명확할 때만 진행한다. 같은 코드에 여러 AI를 상시 병렬 실행해 절감 효과를 가정하지 않는다. 자동 상위 모델 전환은 기존 개발 설정과 예산 정책을 따른다.
F. 인수 기준과 담당
신규 T-ECC-01~06은 ⑦에 등록한 미실행 테스트다. 프로젝트 지침 로드, 실제 검사 실행, 원장 보호, 세션 인계, 사용량 분리, 기존 동작 보존을 확인한다. 기존 T-LG·T-COST·재무 검산의 대체 테스트로 취급하지 않는다.
ChatGPT·Codex는 적용 규칙·검사 절차·설정 변경안·기록을 작성하고 검사를 수행한다. 이승우는 적용 범위·사용성·개발 예산을 검토하고 이재훈은 재무 기준·기대값·독립 검산을 검토한다. 코드·설치·실행의 증거가 확인된 항목만 각 상태를 갱신한다.
G. 공식 근거와 확인일
확인일: 2026.11.01. 아래는 ECC 기능·호환성의 참고 근거이며 dion의 실제 설치·테스트 통과 증거가 아니다. 적용 버전의 문서를 다시 확인한다.

C. 기능 목록(이번 MVP 제안)
F-01 관계 정립: 서비스 목적·AI 한계·가상 고객 모드·분석 범위 제시 및 확인.
F-02 고객 입력: 소득·지출·자산·부채·주거·목표·연금/계좌/투자경험 입력·수정·검증.
F-03 조건부 질문: 고용·주거·대출·연금/자산 계좌 조건에 따라 추가 질문. 질문 이유/미확인 상태 표시.
F-04 현재 진단: 현금흐름·순자산·유동성·비상자금·부채 및 목표 부족액.
F-05 적합성: 투자기간·가용 투자자금·손실 감내 능력·선호·이해도·유동성 제약을 구분해 허용 자산군 판정.
F-06 자산 포트폴리오: 비상자금·주거/단기 목표·연금·장기투자·부채 관리 목적별 배분.
F-07 투자 포트폴리오: 투자 가능한 잔액에 대해 자산군 비중을 제안하고 위험/비용/목표에 따라 필터링.
F-08 금융상품 비교: 검증된 소수의 후보를 공개된 데이터·위험·비용·유동성·세제·추천/제외 이유와 함께 설명.
F-09 시나리오: 실직·시장 하락·물가 상승(기본 3개)의 영향과 제약 위반 여부 비교.

③ 재무·세금·연금 계산 명세 | CALC v2.0
상태: 공식·시점·반올림 확정 필요 | 이재훈: 계산 정의/독립 검산 | 이승우: Python Decimal 구현·pytest
A. 모든 계산식의 표준 작성 양식
calc_id | 목적 | 입력 field_id | 수식 | 계산 단위/통화 | 기준일/시점 | 가정·포함/제외 | 오류·미확인 처리 | 독립 정답 | 반올림 | 법령·출처와 기준년 | 테스트 ID | 승인자.
예: CALC-CASH-01 | 월 가용 현금 | 월 세후소득·소비·부채 원리금·일시비용 | net_income - consumptive_expenses - debt_service - one_off_costs | KRW/월 | 매월 | 원금상환/저축이체 이중 차감 금지 | 결측 → NEEDS_INPUT | 미정 | 원 단위 표시 | 고객 입력 | T-CASH-01.
B. 재무 진단 필수 산식(이전 개발 명세 이동)
CALC-ASSET-01 순자산 = 현금+예금+투자+주택+보증금+기타 자산 − 부채 잔액. 유동화 시점과 과세/거래비용을 별도 기록; 주택·보증금은 즉시 투자 가능 현금이 아님.
CALC-LIQ-01 가용 현금 = 실제 인출 가능한 현금성 자산 − 단기 확정 지출·계약성 자금. 음수/부족 여부 별도 표시.
CALC-EMER-01 비상자금 목표 = 월 필수 소비성 지출 × 목표 유지 개월 수(개월 수는 전문가/고객 결정, 보편적 정답으로 단정하지 않음).
CALC-INVESTABLE-01 투자 가능 금액 = 유동성 있는 금융자산 − 확정 지출 예약액 − 비상자금 필요액 − 목표별 잠금 자금. 음수는 0으로 표시하되 원시 부족액은 별도 경고.
CALC-GOAL-01 목표 원시 격차 = 목표금액 − 목표 시점 사용 가능 재원; 부족액 = max(0,격차), 초과액 = max(0,-격차). 목표 달성률은 성공 확률이 아님.
CALC-CASH-02 소비=돈의 소멸, 저축 이체=자산 내 이동, 대출 원금상환=현금 감소+부채 감소, 이자=소비성 비용. 보증금 지급=현금→보증금 자산 이전. 거래비용만 순자산 소멸.
CALC-DEBT-01 대출 원리금의 잔여 원금/이자 분리. 원금 균등·원리금 균등·만기 일시 등 상환방식, 명목/유효 금리와 월별 이벤트를 명시. 외부 금융상품 대출 조건은 확인된 것만 사용.
CALC-RETURN-01 연 유효 수익률 r의 월 수익률 = (1+r)^(1/12)-1. 월말 납입을 가정하면 월말 잔액 = 전월 잔액×(1+월수익률)+월말 납입액. 이는 계산 가정이지 실제 투자 성과 예측이 아님.
CALC-INFL-01 월 t의 물가 적용 비용 = 초기 해당 비용×(1+연 물가율)^(t/12). 적용 대상 항목·시점·명목/실질 구분·월세 계약성 비용 별도 관리.
CALC-TAX-01 세금 추정: 고객 소득 유형·과세연도·공제·금융소득/상품·계좌별 과세 이벤트에 따라 별도 계산기로 구현. 필요한 정보가 없으면 세제 적용 여부만 설명하고 숫자 산출 보류.
CALC-PENSION-01 국민연금 모의 추정: 공단 공식 계산기와 입력 정의(가입기간·소득 이력 등)를 대조한 범위에서만; 가입 이력 부재 시 신뢰 가능한 수령액으로 표시하지 않음. 퇴직/개인연금은 계좌·납입·수익률 가정 별도.
CALC-PORT-01 투자자산총액 = 현금성+주식형+채권형+기타 허용 자산군의 합(서로 중복되지 않는 투입 금액 기준). 비중 합계 100%, 배분액 합계와 허용 투자금 일치.
C. 시간·정밀도·실패 규칙
t=0 기준 자산과 이후 t=1~N개월 월별 상태를 구분하고, 매월 소득/지출/계약·대출 이벤트→현금 부족 검사→저축·투자 이체→수익/평가→기말 잔액 순서로 계산. 같은 달 계약금 지급/보증금 반환 순서를 명세해야 한다.
Decimal로 내부 산술, 반올림 모드/원 단위 적용 시점/중간 정밀도/허용 오차를 정하고 독립 산식·경계 사례로 검증한다. 값이 입력되지 않았으면 0으로 대체 금지.
세금·수익률·거래비용을 시연에서 제외할 때 결과에 '미반영' 항목을 표시하고 확정 결과처럼 설명하지 않는다.
상태: NEEDS_INPUT(필수값 없음), INFEASIBLE(자금·계약·위험 제약 충돌), READY(검증된 결과), ERROR(시스템 실패), STALE(입력 변경 후 구버전 결과).
D. 과거 기획 검산값(회귀 테스트 전용)
기존 시연: 27세, 세후 월 300만원, 소비 220만원, 현재 월세 보증금 1000만원+주거저축 400만원, 60개월·수익률 0%·물가 0%·이벤트 없음·보증금 전액 목표시점 사용 가능 가정.

상품 비교 항목은 원금손실 가능성·변동성/신용/유동성·비용·세후 가정·보유 기간·계좌 제약·출처/기준일이다. 단순 기대수익률 높은 순 정렬 금지.

screen_id | 목적 | 단계(6단계) | 사용자 행동 | 입력 필드/컴포넌트 ID | API | 상태(빈값/로딩/완료/오류/오래됨) | 에러 메시지 | 저장/이동 조건 | 테스트/와이어프레임 링크.

필수 UX: 모든 금액 단위(원/만원), 과세/자료 기준연도, 가정 여부, 차트 범례·텍스트 설명, 접근성, 모바일 반응형. 색만으로 위험 표시 금지.

[⑥ AI 에이전트·도구·실행기록 명세]
⑥ AI 에이전트·도구·실행기록 명세 | AGENT v2.0
문서 상태: 목표 행동·구조화 출력 초안 / 프롬프트 및 실제 도구 성능 미검증 | 이승우 개발, 이재훈 재무 해설 검토
A. AI 역할/비역할
허용: 고객에게 필요한 질문의 순서 결정, 누락 정보 설명, API 도구 호출, 검증된 결과 해설, 근거 검색·요약, 고객 허용 범위 내 대안 제안, 실행계획 문구 생성.
금지: 확인되지 않은 연금 수령액·세율·상품 위험등급·수수료·수익률·공시 사실의 생성, 상품을 사용자의 조건과 무관하게 추천, 실제 금융상품 매수/계좌 조작, 필수 값 무단 0 또는 평균 대체.
계산·적합성·위험 제약의 최종 판정은 서버의 규칙 및 독립 계산 엔진이 수행한다. 에이전트의 문구가 판단을 뒤집을 수 없다.

TOOL-02 calculate_diagnosis(profile,assumptions) → cashflow, networth, liquidity, debt, goal_gaps, investable_amount. 숫자는 Python에서 생성.
TOOL-03 assess_suitability(profile,risk_constraints) → allowed_asset_classes, blocked_reasons, unknown_fields. 하드 필터는 서버만 판정.
TOOL-04 allocate_assets(diagnosis,goals,constraints) → asset_buckets, debt_plan, reserve_amount. 총액 일치 검증.

TOOL-09 compare_monitoring(previous_run,updated_profile) → changed_fields, new_diagnosis, differences, review_flags.
TOOL-10 fetch_evidence(source_id) → publication_date, observed_date, retrieved_at, url, applicability. 공식 근거만 유효한지 별도 확인.

T-PROD-01: 상품 팩트시트에서 위험/비용/수수료/세제/유동성/출처 중 핵심 정보 누락·정보 오래됨 → 후보 제외/확인 필요.

T-REDESIGN-01: 사용자의 자금 잠금·저축 상한·목표·위험 한도 위반한 대안을 서버에서 거절.

D. 공모전 6단계별 증빙 체크리스트
① 고객과 관계 정립: 분석 목적/한계/정보 이용 확인 기록.
② 정보 수집 및 목표 설정: 기본·조건부 질문, 고객정보표, 미확인 정보 기록.
③ 상황 분석 및 평가: 계산식·재무진단·위험 적합성·세금/연금 가정·독립 검산.
④ 설계안 작성 및 제시: 자산/투자 포트폴리오, 상품 팩트시트, 제외·추천 이유, 스트레스 테스트.
⑤ 실행 지원: 월별 실행 체크리스트, 자금 이동·납입 계획(자동 거래 아님), 고객 승인/보류.
⑥ 실행 경과 모니터링: 가상 점검 시점, 변화 데이터, 경고/재계산, 수정 전후 비교.
E. AI 비판적 검증 실험 설계
개발·튜닝용 가상 케이스와 최종 평가용 케이스를 분리한다(초안 목표 각 10건; 공모전 의무 수량이 아님). 동일 조건으로 일반 AI 답변과 도구 연결 답변을 비교.
정량 지표 후보: 필수 질문 누락률, 계산 오차, 적합성 위반률, 공시/출처 누락률, 시나리오 위험 경고 적중, 해결 가능한 수정안 비율, 응답 지연과 API 사용량.
정성 평가 후보: 상품 설명의 이해 가능성, 위험·세제의 균형, 고객 목표 부합성, 제약 및 불확실성 표현.
검증 증거: 입력→AI 최초 답→실패/반례→독립 계산·공식 자료→수정답→재계산→채택 이유. 실패를 만들어냈다고 주장하지 않고 실제 발생한 사례만 기록.
