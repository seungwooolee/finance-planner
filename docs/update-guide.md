# 버전·PR 진행 원칙 — 2026-11-14 사용자 결정

- 의미 있는 기능 묶음을 한 버전·한 PR로 진행한다. 단순 수정마다 새 버전이나 PR을 만들지 않는다.
- 관련 검사1회를 기본으로 하고 새 변경/실패가 없으면 통과한 검사를 반복하지 않는다. 금융 계산·인증·개인정보·보안 핵심 검사는 유지한다.
- 로컬 커밋→승인된 푸시→PR의 기존 CI 확인→승인된 병합 순서로 진행한다. 전체 빌드/E2E는 영향상 필요할 때만 실행한다.
- 푸시·병합·배포 승인과 자동 배포 연결은 구분한다. 앱 버전은 frontend/package.json·package-lock.json의 루트 버전을 맞추고 CHANGELOG.md에 기록한다. 의존성·엔진/API·사례 버전은 자동 변경하지 않는다.
- 이번 v0.2.0은 로컬 통합 버전이며 배포/운영 검증 완료를 뜻하지 않는다.

## 언제 업데이트하는가

정해진 주기보다 변경이 생긴 시점에 전달하면 된다. 질문·선택지 변경, 디자인 확정, 계산정책 결정, 실제 코드 수정, 새 오류가 생겼을 때 업데이트한다. 변경이 없으면 같은 파일을 반복 업로드하지 않아도 된다.

| 바뀐 것 | 사용자가 전달할 내용 | 함께 반영할 내용 |
| --- | --- | --- |
| 디자인 | HTML/ZIP과 화면명·변경 의도·대체 여부 | 날짜별 원본·디자인 검토·화면 연결 |
| 질문·선택지·조건 | 변경 원본과 이전→이후 | 현행 질문·Q-ID/필드/enum/조건 대조 |
| 계산·배정 정책 | 결정 내용·이유·적용 대상·예시, 확정/검토 구분 | 정책·명세·독립 기대값·영향 검사 |
| 로컬 코드 | 최신 프로젝트 ZIP 또는 GitHub 브랜치·커밋 | 기존 구조에서 필요한 코드와 문서 |
| 오류 | 실행 동작·기대 결과·실제 결과·오류 전문 | 재현·수정·검사·실행 기록 |

## 같은 대화에서 이어가기

1. 변경 자료만 첨부하고 원하는 범위를 쓴다: 원본 보관 / 적용 전 검토 / 실제 앱 구현.
2. 이전 자료를 대체하는지, 별도 시안인지 표시한다. 예: 월간 기록 PC v2로 교체, 모바일 유지.
3. 받은 최신 통합본을 다음 작업의 기준으로 사용한다. 미확정 질문·정책은 자동 확정하지 않는다.
4. GitHub 코드도 바뀌었다면 브랜치·커밋을 함께 알려준다. 로컬 ZIP과 원격 중 최신을 추정해 덮어쓰지 않는다.

## 새 대화나 다른 계정에서 이어가기

1. 가장 최근 finance-planner 통합 ZIP 하나를 올린다.
2. 아래 양식을 붙여넣는다.
3. 루트 README → AGENTS → docs/project-status.md → 관련 명세 순으로 읽고 기존 구현을 재사용하게 한다.
4. 전체 통합본이 있으면 예전 Handoff·Continuation ZIP을 다시 전부 올리지 않아도 된다. 접근되지 않는 파일만 추가한다.

## 이번에 반영한 것

기존 실행 코드 전체와 최신 Continuation 자료를 한 폴더에 모았다. 재방문 대시보드·월간 기록 PC·모바일 HTML을 분리하고 [적용 전 수정사항](design/2026-11-10/README.md)을 기록했다. 질문·계산정책·런타임 코드의 의미는 바꾸지 않았다.

## 최신본 관리

GitHub를 쓰면 저장소를 코드 기준으로 관리하고 다른 대화로 넘길 때 같은 상태의 통합 ZIP을 만든다. 로컬에 미반영 변경이 있으면 그 ZIP도 제공한다. 이전 프로젝트 첨부를 최신 ZIP으로 교체해 기준을 하나로 유지하고, 보관용 과거판은 날짜/버전을 붙여 별도로 둔다.

사용자가 여러 문서를 직접 고칠 필요는 없다. 변경 원본과 의도를 보내면 관련 파일·현황·검사 기록을 함께 갱신하는 방식으로 진행한다. 전체 ZIP에서는 node_modules·.venv·.next·로그·비밀값을 제외한다.
