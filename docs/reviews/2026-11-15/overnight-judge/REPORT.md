## AI와 RAG 평가

- **잘 된 점:** 저장된 금액·기간·구성 revision을 근거로 설명하고, 모델이 새 금액을 만들어 확정하지 않도록 서버가 검증한다. L10은 이미 확인한 개인 범위를 다시 묻지 않고 두 안을 설명했다. 실제 R3와 월 코치는 원래 진단·채택을 바꾸지 않았다.
- **실제 실패:** 주입 L8은 공급자 응답 뒤 `CHAT_REPLY_UNGROUNDED`로 차단되어 503이 됐다. 타인 정보·비검증 답변은 노출되지 않았다. 그러나 친절한 거절 응답의 성공은 아니다.
- **이해도 개선:** L4는 두 안을 묻는 질문에 선택된 안정안 설명이 중심이다. L11은 후보금과 현금의 의미를 물었는데 수치·상품·한계를 길게 나열한다. 정확성 보호를 유지하며 첫 결론과 용어 설명을 개선할 가치가 있다.
- **상품 고유 RAG:** `PRD-069500` 설명은 `FALLBACK/NO_APPROVED_EVIDENCE`, 인용 0개였다. 예시 평가일은 11월13일, 등록 자료 효력 시작은 11월15일이다. 이 경계를 해제해 성공으로 만들면 안 된다.
- **일반 개념 RAG:** 같은 상품의 위험 개념 `CON-01`은 실제 등록 인용을 반환했다. 별도로 실제 OnePort selector를 연결한 L13도 답변·인용을 반환했다. “RAG 전체가 안 된다”는 결론은 틀리다.
- **평가 모델의 한계:** 별도 채점 3개는 E/R3 실호출과 L13 추가 전에 수행됐다. 그 결과를 추가 사례의 별도 모델 재평가처럼 사용하지 않았다. 채점 모델이 원본 응답만으로 실호출 여부를 확정할 수 없다고 한 부분은 별도 영속 영수증으로 대조했다. 모델 의견을 자동 정답으로 채택하지 않았다.

6단계의 코드·계약 연결은 존재하며 분석과 이력 보존은 강점이다. 다만 **가구·은퇴를 포함한 모든 고객의 6단계가 완전하게 계산·검증됐다는 주장은 현재 증거보다 넓다.**

## 먼저 고칠 항목

관찰된 P0는 0건이다. 전체 웹·실인증이 미검증인 상태에서 P0가 없다고 보증하지 않는다. [전체 피드백 11건](findings.json)은 P1 4건/P2 7건이며 표현 문제·실제 API 문제·지원 한계·검증 공백을 구분했다.

| 1 | 01 | 수익 0%를 가장 보수적이라고 부르는 문구 수정 | S |
| 2 | 02 | 이번 달을 실제 계획 월·기록 월로 구분 | S |

| 5 | 05 | 주입/검증 실패의 안전한 사용자 안내 | S–M |

다음 작업은 세 묶음이면 충분하다. (1) 결과 화면의 날짜·전망·완료/현금·채택 표시, (2) AI의 설명·안전 안내, (3) 버전이 고정된 시연 사례와 실제 웹 연결. 새 기능을 늘리기 전에 이 세 묶음의 증거를 마무리하는 편이 심사 설명에 효과적이다.

## 심사위원 관점

실제 차별점은 챗봇의 문장 생성 자체보다 **원응답→정확한 계산→근거 있는 설명→사용자 확인→별도 채택→불변 실적→새 초안**의 연결이다. AI를 제거해도 계산과 기록은 유지되지만, 자연어 사실 추출·결과 질문·가상 조건 해석·다음 점검 안내의 접근성이 사라진다. 이 부분을 실제 금액·변경 전후·저장 버전과 함께 보여줄 때 AI의 필요성이 가장 설득력 있다.

| 예상 질문 | 현재 답할 수 있는 근거 | 추가 준비 |
|---|---|---|
| 1. 일반 챗봇과 무엇이 다른가? | 저장 결과·출처·버전으로 생성 범위를 제한하고 확인·채택을 분리 | 짧은 실제 대화와 변경 전후 화면 |

## 운영 관찰과 남은 검증

[공개 GET 관찰](evidence/operational-get.json)에서 최초 `/health`는 25초 내 응답을 받지 못했다. 뒤의 `/readyz`는 200/ready, DB READY, 인증 CONFIGURED_NOT_PROBED였다. BE 식별은 `5e515f8`, corpus 65개와 dialogue 경로 등록을 반환했다. Vercel 프록시 식별 요청은 비인증 401이었다. 이 한 번의 관찰로 장애 원인이나 SLA를 확정하지 않았다.

운영 SHA와 감사 SHA는 다르다. 두 버전의 `backend/app`·`frontend/src`를 대조해 런타임 차이가 없음을 확인했지만, 실제 인증·DB 쓰기·브라우저 연결 성공을 대신하지는 않는다. 운영 설정·예산·고객 기록을 변경하지 않았다.

브라우저 제한은 [별도 기록](evidence/browser-limitations.json)에 있다. 자동 승인 검토가 전용 FE/BE 서버 시작을 `blocked by policy`로 거절했으며 구체 사유는 제공되지 않았다. 같은 시작을 다른 수단으로 우회하지 않았다. 기존 미리보기는 SHA를 보증할 수 없고 도중 중단/500이어서 기준본의 제품 결함으로 단정하지 않았다. 다른 사람이 시작한 서버와 브라우저는 종료하지 않았다.

최종 판단: **핵심 재무·서버 경로의 검증 증거는 확보했다. 상품/설명/기간 표현과 시연 사례를 정리하고 정상 환경의 전체 웹·실계정 복원을 확인하기 전까지, 전체 고객 여정 검증 완료 또는 운영 무결점으로 표현하지 않는다.**
